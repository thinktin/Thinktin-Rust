## 第 1 轮：产品构想

**用户**

> 我想做一个产品，就是云端部署多个agent，然后用户注册了我平台的账号就可以领养我发布的agent用来私用，但我希望这种用户之间是隔离的，每个人注册都能领养自己云端常驻agent。然后我的产品可以装在电脑上，也可以装在手机上。安装电脑客户端的用户且电脑端有登录和授权的情况下，还可以用手机控制agent执行电脑的任务。正常情况下，用户可以用手机安排云端agent执行任务。

**回答**（Claude Sonnet）

这个产品完全可行，核心是"控制面 + 每用户隔离的运行时 + 设备中继"三层。

**1. 云端：模板与实例分离**
- 你发布的是 **Agent 模板**（带版本号的镜像、提示词、工具配置）。用户"领养"就是为他创建一个独立的 **Agent 实例**。
- 每个实例一个隔离沙箱：容器加 gVisor，或 Firecracker microVM。要求更高时，每用户单独一个 K8s namespace。
- 每个用户有独立的存储、记忆/向量库、密钥，数据库全程带 tenant_id 并开启行级安全。密钥用 KMS 按用户分别加密，出站网络按白名单限制。
- "常驻"不等于一直占着资源：空闲时休眠，状态落盘，有任务或定时触发时再唤醒，成本会低很多。
- 所有模型调用都走你自己的 LLM 网关，按用户限额、计费、审计。

**2. 手机 → 云端 Agent（常规路径）**
手机 App 只是客户端：登录后提交任务，任务进队列，由该用户的实例执行，结果通过推送和 WebSocket 回传。

**3. 手机 → 电脑（关键难点）**
- 电脑客户端运行本地守护进程，**主动向外连接**你的中继服务（WebSocket/QUIC），不开放入站端口，这样能穿透 NAT。
- 设备配对：电脑端登录后生成设备密钥并绑定账号，手机端扫码或确认。
- 链路是：手机 → 云端 Agent → 中继 → 电脑守护进程。云端 Agent 把电脑当成一个"远程工具"来调用。
- 权限分级：只读（看文件、截图）、可操作（打开应用）、高危（删除文件、支付、执行命令）。高危操作必须在手机上二次确认，且电脑端有授权开关，可一键断开。
- 电脑端要有完整操作日志，并且让用户能随时看到"Agent 正在控制我的电脑"。

**4. 要提前想清楚的风险**
- **提示注入**：Agent 读到的网页或邮件可能诱导它操作用户电脑，所以电脑端工具权限要最小化，不要让一次授权变成永久全权。
- 设备令牌被盗：令牌要短期有效、可吊销，并绑定设备。
- 合规：如果面向国内用户，要考虑数据出境、模型备案和个人信息保护。

**5. 建议的 MVP 顺序**
1. 先做云端：账号 → 领养 → 独立沙箱实例 → 手机下发任务。
2. 再做电脑客户端的中继和配对，先只开放只读工具。
3. 最后加高危操作确认、审计、休眠唤醒优化。

技术栈上，客户端可以用 Flutter 或 Tauri，加 React Native 做手机端。后端用 Go 或 Node，K8s 做编排，Postgres 加 Redis 加对象存储。

你更想让我展开哪部分：整体架构图、数据库与隔离设计，还是电脑端的授权与安全模型？另外，你的 Agent 是自研框架，还是基于现有的 Agent SDK？

## 第 2 轮：K8s namespace 是什么

**用户**

> K8s namespace是什么

**回答**（Claude Sonnet）

Namespace 是 Kubernetes 里的"逻辑隔离分区"，可以理解成集群里的一个独立文件夹或小房间。

**它能做什么**
- 把资源（Pod、服务、密钥、配置等）按组划开。同一个集群里，A 用户的东西放在 `user-a` 这个 namespace，B 用户的放在 `user-b`，互相看不到、重名也不冲突。
- 可以给每个 namespace 单独设置：
  - **资源配额**：这个用户最多用多少 CPU、内存、存储
  - **访问权限（RBAC）**：谁能操作这里面的东西
  - **网络策略**：默认禁止和其他 namespace 的 Pod 互相通信
  - **密钥**：Secret 只在本 namespace 内可见

**放到你的产品里**
用户领养 agent 时，系统自动创建一个 `user-12345` 的 namespace，里面放这个用户的 agent Pod、存储卷和密钥，再加上配额和网络策略。用户注销时，删掉这个 namespace，里面所有东西一起清理干净，很方便。

**要注意它的局限**
Namespace 只是**逻辑隔离**，不同用户的 Pod 仍然可能跑在同一台物理机、共享同一个内核。如果 agent 会执行用户代码或命令，光靠 namespace 不够，还需要配合 gVisor 或 Firecracker 这类沙箱，防止容器逃逸。另外，用户量很大（几万以上）时，一人一个 namespace 会给集群带来管理压力，可以考虑按用户分组，或者只对高价值用户这样做。

简单说：namespace 管"资源和权限的归属边界"，沙箱管"代码执行的安全边界"，两者要搭配使用。

## 第 3 轮：重新梳理，考虑成本和强隔离，用 Rust 开发

**用户**

> 我觉得sonnet回答的不好，你梳理一下给我回复，另外帮我考虑成本和强隔离，我希望用rust开发

**回答**（Claude Opus）

结论：架构定为**「大脑共享、手脚隔离；逻辑常驻、物理按需」**。除了界面层，其余部分都可以用 Rust 写。和前面的方案相比，有三处关键调整：

1. **强隔离靠 microVM，不靠 K8s namespace。** namespace 只是管理分组，不提升隔离强度，也不需要一人一个。
2. **agent 的"大脑"和"手脚"要拆开。** 大脑多租户共享，执行环境每人独立、按需启动，这是省钱的关键。
3. **手机上的确认要做成电脑能验证的签名。** 否则云端被攻破或 agent 被提示注入时，确认就形同虚设。

### 一、整体架构

**领养模型**：你发布带版本的 agent 模板，包括提示词、工具和沙箱镜像。用户领养时，系统给他生成自己的实例，记忆、配置、工作区都独立。隔离边界是"用户"，同一用户领养的多个 agent 共用一个沙箱。

- **控制面**（共享、无状态、可水平扩展）：接入网关、大脑服务（agent 循环、任务队列、定时触发）、模型网关、设备中继
- **执行面**（每用户独立）：云端每人一个 microVM，有活才开；用户电脑上的守护进程在授权范围内执行

三条链路：
- 手机 → 大脑 → 用户的云端沙箱
- 手机 → 大脑 → 中继 → 用户电脑
- 定时/事件 → 大脑 → 唤醒沙箱

"常驻"指身份、记忆、定时任务一直都在，机器只在干活时才开。大脑可以共享，是因为 agent 大部分时间都在等模型返回。AWS 的同类服务也是这个思路：每个会话一个独立 microVM，但 CPU 只按实际计算量计费，等模型响应的时间通常不收钱。

原则：**大脑只处理结构化消息；执行代码、打开网页、解析文件，一律放进沙箱。**

### 二、强隔离

- **计算**：每人一个有独立内核的 microVM，靠 KVM 硬件虚拟化隔离，比共享内核的容器强得多。
- **网络**：沙箱之间默认不通，禁止访问云元数据服务和你的内网。出网走代理，加白名单和限速。
- **数据**：每个用户一把数据密钥（KMS 信封加密）。对象存储按用户分前缀，只发临时凭证；数据库开 RLS 兜底。用户注销时删掉密钥，数据就无法恢复。
- **凭证**：用户授权的第三方令牌不进沙箱，由出口代理在发请求时注入。沙箱即使被攻破，也拿不到令牌原文。
- **大脑层**：工具调用的目标（哪个沙箱、哪台电脑）只由会话绑定决定，绝不取自模型输出。数据库访问统一走一个必须传入 `TenantCtx` 的仓储层，由它自动加租户条件，业务代码想漏也漏不掉。
- **企业版**：独占物理核或专属宿主机，防 CPU 侧信道。

**沙箱选型**：推荐腾讯云开源的 CubeSandbox。
- 今年 4 月以 Apache 2.0 开源，放出的是整套生产级沙箱服务，不只是 SDK。
- 底层是 rust-vmm 加 KVM，每个沙箱有自己的内核。冷启动不到 60 毫秒，每个实例只多占不到 5MB 内存，一台机器能同时跑两千多个。沙箱间网络隔离和出网黑白名单靠 eBPF 实现，接口兼容 E2B SDK。
- 代码以 Rust 为主，和你的技术栈一致。
- 运行需要开启 KVM 的 Linux，物理机或云裸金属都行，开发时用 WSL 2 也可以。

不过项目很新，社区对它离开腾讯自家环境后能否稳定用于生产仍有疑问，代码里要留退路。备选是直接用 Firecracker（AWS 开源，也是 Rust 写的），但调度、快照、网络都得自己做。

### 三、成本

大头通常依次是：**模型 token > 沙箱算力 > 存储 > 出网流量**。

**算力：按需启动**

假设 1 万注册用户、日活 30%，活跃用户每天沙箱实际运行 20 分钟，每个沙箱 1 核 1G：
- **每人常开**：1 万个 VM、约 10 TB 内存，要几十台大服务器。
- **按需启动**：平均并发 ≈ 1万 × 30% × 20 ÷ 1440 ≈ 42 个。按 4 倍峰值留余量约 170 个，常见规格的裸金属两台（含一台冗余）就够。

两者差距在几十倍。沙箱再分三级状态：
- **热**：运行中
- **温**：暂停并存快照，释放资源，恢复快
- **冷**：销毁沙箱，工作区打包进对象存储

**存储**：所有人共享只读的模板镜像，每人只存自己的增量，放对象存储。不要给每人挂一块云盘：假如每人 20 GB，1 万人就是 200 TB 常年计费。记忆和向量用 Postgres + pgvector，不单独上向量库。

**Token**
- 给每个用户设预算硬上限，单个任务限制最大步数，防止 agent 死循环烧钱。
- 收费用"订阅 + 额度"，让成本随用量转嫁给用户。
- 简单步骤用便宜模型，规划和关键决策用强模型。
- 系统提示和工具定义保持固定前缀，尽量命中提示缓存；长上下文做压缩，工具输出做截断。
- 电脑操作优先用结构化工具，少用截图，截图很费 token 和带宽。

**防滥用**：免费沙箱一定会被拿去挖矿、做代理、发垃圾邮件。要限制 CPU 时长，出网用白名单，注册要验证手机号。

**Rust 的红利**：中继单机能挂数万条长连接；大脑里每个会话只是一个轻量异步任务，几个核就能同时挂住大量在等模型的会话。

### 四、手机控制电脑

- **组成**：电脑端由图形界面（登录、授权设置）和后台守护进程组成。系统层面还要用户授予辅助功能、屏幕录制等权限。
- **连接**：守护进程**主动连出**到中继（wss 走 443 端口，公司网络也能通），不开任何入站端口。
- **配对**：每台设备生成自己的密钥对，私钥存在系统钥匙串里。手机扫电脑屏幕上的二维码，二维码里带一次性配对密钥，这个密钥不经过云端。双方据此交换公钥，云端无法冒充任何一方。
- **工具化**：电脑端本质上是一个经中继暴露的 **MCP 工具服务**，大脑像调用普通工具一样调用它。
- **普通权限**：用能力令牌（如 Biscuit）限定可访问的目录、应用和有效期，可随时吊销，由电脑本地校验。
- **高危操作**（删除、执行命令、发送、支付）：手机确认后用手机私钥签名，电脑验签通过才执行，云端伪造不了。
- **可见可控**：电脑上始终显示"正在被控制"的提示，提供一键停止快捷键和本地审计日志。

### 五、Rust 技术栈

```
crates/
  proto        共享协议与类型
  gateway      接入网关
  brain        agent 循环与调度
  llm-gw       模型网关
  relay        设备中继
  sandbox      沙箱抽象层
  desktop      电脑端守护进程
  client-core  客户端共享核心
```

- **服务端**：tokio、axum、sqlx、rustls。Postgres 存业务数据，同时承担 RLS、pgvector 和任务队列；Redis 存在线状态和路由；另加对象存储。
- **Agent**：自己写循环，调 OpenAI 兼容接口（国内主流模型基本都提供）。工具协议用官方的 MCP Rust SDK（rmcp）。
- **电脑端**：enigo 控制键鼠，xcap 截图，chromiumoxide 控制浏览器，keyring 存密钥。
- **界面**：推荐 Flutter，一套代码覆盖手机和电脑，通过 flutter_rust_bridge 调用 Rust 核心。如果团队更熟 Web，可以用 Tauri 2，但手机端接推送要自己写原生插件。
- **推送**：手机后台的长连接会被系统杀掉，任务结果必须走推送。iOS 用 APNs；国内安卓要接各厂商的推送通道，或者用极光、个推这类聚合服务。

### 六、落地路线

1. **上线初期**：用户少的时候用托管沙箱，按量付费，没有闲置成本。可选阿里云函数计算 AgentRun（内置代码解释器、浏览器等沙箱），或腾讯云 Agent Runtime（VM 级隔离，每个任务有独立资源边界）。沙箱在代码里抽象成一个 trait，本地开发时可以用 WSL 2 跑 CubeSandbox 调试。
2. **规模期**：当托管账单持续超过几台裸金属的月租时，自建 CubeSandbox 集群，单位成本最低。
3. **电脑端**：先上只读工具（看文件、截图），再开放操作类工具，最后上签名审批。

国内上线还要准备 ICP 备案、等保、生成式 AI 服务的备案或登记，以及个人信息保护。前面"删密钥即销毁"的设计正好能满足注销删除的要求。

## 第 4 轮：CubeSandbox 和 Firecracker 哪个更强

**用户**

> CubeSandbox和Firecracker哪个更强

**回答**（Claude Opus）

结论：**隔离强度打平；Firecracker 更成熟，Cube 更完整。你的项目选 Cube。**

两者其实不在同一层。Firecracker 是"发动机"，只负责把 microVM 跑起来。CubeSandbox 是"整车"，调度、网络、快照、API 都自带。分维度看：

- **隔离强度：打平。** 两者是同一类技术，都是跑在 KVM 上的 microVM，每个沙箱有独立内核，核心虚拟化层也都是 Rust。Cube 用的是腾讯自己基于 rust-vmm 写的 CubeHypervisor，并不是在 Firecracker 外面套一层壳。
- **成熟度：Firecracker 明显更强。** 它从 2018 年起就承载 AWS Lambda 级别的生产流量。Cube 这套技术虽然在腾讯内部跑过一阵，但公开的时间还很短。另外，Firecracker 刻意只保留极少的虚拟设备，攻击面更小。
- **开箱即用：Cube 明显更强。** 用 Firecracker，调度、网络、出网过滤、模板构建、快照管理和对外 API 都得自己搭。Cube 都已经带了：
  - 用 eBPF 虚拟交换机做网络隔离，出网网关会拦截沙箱发出的每个 HTTP 请求。
  - 运行中的沙箱可以打检查点、回滚到任意保存的状态，或者分叉成多个并行环境，适合让 agent"先试，出错再撤销"。
- **性能：纸面接近。** 两者单实例额外内存都不到 5MB。Cube 的 60 毫秒冷启动靠的是资源池预置和快照克隆。Firecracker 官方的约 125 毫秒是不带预热的裸启动，基于它的平台加上快照也能做得很快。
- **部署门槛：Cube 更灵活。** Cube 现在支持 PVM 模式，能跑在普通云主机上，不需要裸金属或嵌套虚拟化，代价是冷启动比裸金属慢三到四成。Firecracker 则必须有 KVM。

**为什么你该选 Cube**

小团队直接用 Firecracker，等于先花几个月自己造一个 Cube。只有当你有专职的基础设施工程师、又需要深度定制虚拟化层时，Firecracker 才划算。

Cube 的风险在于太新，所以上线前要自己做压测和安全评估。退路是现成的：业务代码按 E2B 接口来写，而 E2B 本身开源（Apache 2.0），底层就是 Firecracker。哪天 Cube 出问题，换成 E2B 的托管服务或自建版本，业务代码基本不用改。

PVM 模式对早期省钱也有用：可以先在普通云主机上跑 Cube，用量上来再换裸金属。

## 第 5 轮：新需求——全部用开源 agent，可配置各厂商 key

**用户**

> 你把以上对话添加到我thinktin-rust项目里呗？另外就是agent不自己开发，全使用开源agent，云端会部署多个开源agent，另外还有就是可以配置各厂商的LLM key

> （补充）就手机端的app里Claude的项目啊啊

**处理**（Claude Opus）

- Claude 没有往 Claude 项目里写文件的工具，所以把内容整理成两个 markdown 文件，由用户加入 thinktin-rust 项目的知识库：本记录，以及《ThinkTin 平台架构方案 v2》。
- 新需求带来的主要调整（详见方案 v2）：
    - 不再自研 agent 循环。每个开源 agent 实例整个跑在自己的 microVM 里，沙箱内由 Rust 写的 `agent-shim` 用 ACP 驱动 agent，用 MCP 注入平台工具和电脑工具。
    - 新增 Agent 目录：每个上架的 agent 是带版本的模板，附带启动和接入清单。首批建议 Hermes Agent、ZeroClaw、Goose。
    - 新增 BYOK：密钥库（信封加密）加模型网关（协议透传、换 key、计量、限额、SSRF 防护）。key 永不进沙箱。
    - 成本结构变化：token 由用户直付厂商，平台的最大成本变成沙箱算力。
    - 合规：国内站只接入已备案的国内模型；OpenAI、Anthropic 对中国有访问限制，放到独立的海外站。

## 后来被修正的结论

| 原结论（轮次） | 修正后 | 原因 |
|---|---|---|
| 大脑共享、手脚隔离（第 3 轮） | 取消共享大脑，每个开源 agent 实例整个跑在自己的 microVM 里 | agent 改用开源项目，它们都是完整程序 |
| 同一用户领养的多个 agent 共用一个沙箱（第 3 轮） | 每个 agent 实例一个沙箱，同一用户的实例可共享工作区卷 | 不同 agent 运行时差别大，各用各的模板更简单 |
| crate 中有 `brain`（自研 agent 循环）（第 3 轮） | 删除 `brain`，新增 `control`、`catalog`、`agent-shim`、`keyvault` | 不再自研 agent |
| 成本大头是模型 token（第 3 轮） | BYOK 下 token 由用户承担，平台最大成本是沙箱算力 | 用户自带各厂商 key |
| CubeSandbox 需要开启 KVM 的 Linux（第 3 轮） | 也支持 PVM 模式，可跑在普通云主机上，冷启动慢三到四成 | 第 4 轮查到的新信息 |
| 每个实例一个沙箱：容器加 gVisor 或 Firecracker（第 1 轮） | 首选 CubeSandbox，按 E2B 接口编码，保留切换到 E2B（Firecracker）的退路 | 第 3、4 轮的选型结论 |
