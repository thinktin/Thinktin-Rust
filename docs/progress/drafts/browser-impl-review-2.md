## shim-service

### tools::load adds "required": null to every kept tool schema that has no required list, so MCP TypeScript clients reject the whole thinktin tools/list

- 位置：`crates/agent-shim/src/browser/tools.rs:62`；评审定的严重程度：high；核对：**成立**（high）
- 场景：The new schema edits use serde_json IndexMut: `t["inputSchema"]["required"].as_array_mut()` (and the `properties` line above it) inserts a Null for a missing key before `as_array_mut()` returns None. In the real 0.0.84 tools.json, five kept tools have no `required`: browser_close, browser_find, browser_navigate_back, browser_snapshot and browser_wait_for. I ran the same statements on scratchpad/pwmcp/tools.json and all five came out with `"required": null`. A schema `{}` becomes `{"properties":null,"required":null}`. Bridge::tool_list passes inputSchema to the agent unchanged. I checked @modelcontextprotocol/sdk 1.31.0 (OpenClaw image) and 1.32.1 (claude-agent-acp image): ListToolsResultSchema rejects it with 'tools.N.inputSchema.required: expected array, received null', so client.listTools() throws. Claude Code, OpenClaw and Pi then get no thinktin tools at all, including web_search and the platform tools, whenever the browser is on. The smoke test calls BrowserService directly with no MCP client, so it cannot see this.
- 建议：Do not index mutably into keys that may be missing. Use `if let Some(p) = t.pointer_mut("/inputSchema/properties").and_then(Value::as_object_mut) { ... }` and `if let Some(r) = t.pointer_mut("/inputSchema/required").and_then(Value::as_array_mut) { ... }`. Add a unit test: a schema without `required` (and `{}`) comes out of load() unchanged, apart from `filename` and `_meta` being removed.
- 核对理由：Confirmed. tools.rs:57 and :62 call `.as_object_mut()` / `.as_array_mut()` on `t["inputSchema"][...]`. That makes Rust use IndexMut, and serde_json's IndexMut inserts Null for a missing key before the method runs. I copied the two statements into a scratch crate (serde_json 1.0.154) and ran it on the real 0.0.84 tools.json. browser_close, browser_find, browser_navigate_back, browser_snapshot and browser_wait_for (all in KEEP) come out with `"required": null`. Bridge::tool_list (bridge.rs:372-385) and run_client/keep_only (bridge.rs:585-590, 677) pass inputSchema through unchanged. Pi and OpenClaw are given search plus the browser tools (config.rs `--only` list), so they are affected too. I checked the clients with node. ListToolsResultSchema in @modelcontextprotocol/sdk 1.32.1 (claude-agent-acp image) and 1.31.0 (openclaw image) rejects the result: 'tools.0.inputSchema.required: Invalid input: expected array, received null'. Claude Code's cli.js calls `client.request({method:"tools/list"}, Gu1)`. Gu1 uses the same `required: B7(l6()).optional()` schema, and a failure goes to `catch` 'Failed to fetch tools', so the whole server's tools are dropped. Nothing tests this: `cargo test -p agent-shim browser` passes (14 ok), the unit test only checks that filename is gone, and browser_smoke calls BrowserService directly with no MCP client.
- 核对建议：In tools::load, replace the two IndexMut lookups with non-inserting ones: `if let Some(p) = t.pointer_mut("/inputSchema/properties").and_then(Value::as_object_mut) { for k in STRIPPED_ARGS { p.remove(*k); } }` and `if let Some(r) = t.pointer_mut("/inputSchema/required").and_then(Value::as_array_mut) { r.retain(...) }`. Add a unit test: a kept tool whose schema has no `required` (and one with `{}`) comes out with no `required` or `properties` key added.

### The run and pass checks run before the new call lock; queued calls run after TurnEnded or stop()

- 位置：`crates/agent-shim/src/browser/mod.rs:243`；评审定的严重程度：low；核对：**成立**（low）
- 场景：call() checks `self.run` (line 232) and the pass (line 235) and only then waits on `self.calls.lock()` (line 243). Nothing is checked again once the lock is held. The bridge spawns every call and never cancels it. Example: Claude sends [browser_navigate(a), browser_navigate(b), browser_navigate(c)] in parallel. The user stops the turn while a's ask is waiting. TurnEnded runs end_run, which clears `run` and the approvals. b and c are still queued and then run one at a time, up to 55 s each, after the turn has ended. They navigate the browser and send new /v1/browser/ask requests, so approval cards appear after the user stopped the task. Their approve/deny calls go into the cleared approvals and can carry into the next turn. If the next turn has started, its first browser call also waits behind them. Before the lock, a call that arrived after end_run was refused, and nothing started later than when it arrived. After BrowserService::stop(), a queued call goes on to ensure() and starts a new Chromium and Playwright during shutdown.
- 建议：Read the run id before taking the lock. After `self.calls.lock().await`, check that `self.run` still holds that id and that pass_value(&self.pass) is still Some, and return the same errors as at the top of call() if not. Optionally have stop() set a flag that ensure() checks, so nothing starts after shutdown.
- 核对理由：Confirmed regression from c7b2fea. In call() (mod.rs:228-243) the `self.run` check and the pass_value check come before `self.calls.lock().await`, and nothing is checked again after the lock is taken. Bridge::serve_conn (bridge.rs:472-479) tokio::spawns each call. MCP notifications, including notifications/cancelled, are ignored (bridge.rs:608-611), so a stopped turn cancels nothing in the shim. Claude Code runs readOnlyHint tools concurrently (`isConcurrencySafe(){return z.annotations?.readOnlyHint}`), and load() marks every browser tool read-only. So [navigate a, navigate b, navigate c] in one message reaches call() together: a takes the lock, b and c queue. If the user stops while a's ask waits, main.rs:522 runs end_run, which clears `run` and the approvals. b and c then run one after another (up to 55 s each): they navigate and POST /v1/browser/ask. verify_browser_pass is not tied to the run, so new approval cards appear after the stop. If begin_run has already happened for the next turn, that turn's first browser call waits behind them. Before the lock these calls would have started at once, before the stop, so starting after TurnEnded is new. The stop() part is minor: the shim exits right after, and a session started then dies with its pipes. Late answers going into the next turn already existed for asks in flight before the fix. Impact is confusing UX and wasted browsing, no security effect.
- 核对建议：Before the lock, read `let run = self.run.lock()...clone()` (refuse if None). After `let _one_at_a_time = self.calls.lock().await;`, refuse with the same errors as the top of call() if `*self.run.lock() != run` or `pass_value(&self.pass).is_none()`. stop() already clears the pass, so the second check also stops queued calls from starting a new Chromium during shutdown.

### Ask outcomes are still filed under the call that is running when the ask finishes, so another call can get a wrong first line

- 位置：`crates/agent-shim/src/browser/mod.rs:265`；评审定的严重程度：low；核对：**成立**（low）
- 场景：wait_asks/asking_since only cover asks that started after this call's `started`. The gate still records the outcome with `at = Instant::now()` when the ask finishes (gate.rs:477), and outcomes_since(started) filters on that time. So this part of the original finding is still open in three cases: an ask that starts between calls (a JS timer or meta-refresh navigation, or a popup after the click returned), an ask that outlives the previous call's 55 s deadline, and an ask from the previous turn, whose `asking` entry clear() keeps. Example: page A runs `setTimeout(() => location = 'https://x.example/', 2000)` and the click returns first. x.example's ask runs about 40 s. Meanwhile the agent calls browser_navigate(y.example), and the user approves y at second 38. X finishes 'pending' at second 40, during that call. tools::status picks the last non-allowed outcome, so the navigate to y reports 'pending_approval: opening x.example ... call browser_navigate with this URL again later', although y opened.
- 建议：Record an ask's outcome with the time the ask started. For example, keep the start Instant in `Asking` and add `Asking::finish(self, result, asked)`, which pushes `Outcome { at: start, .. }` and then unregisters. outcomes_since(started) then only returns asks that began during this call, and these are exactly the ones wait_asks waits for.
- 核对理由：The fix closes only half of the original finding ('the outcome lands on an unrelated later call'). wait_asks and asking_since filter on the ask's start time (approvals.rs:103-125). But gate.rs:477 still calls `approvals.record(...)`, which stamps `at: Instant::now()` when the ask finishes (approvals.rs:226-231), and call() filters with outcomes_since(started) on that time. So an ask that started outside the current call, and finishes during it, still lands in that call's outcomes. That covers three cases: a JS timer or meta-refresh navigation after the click returned; an ask that started late in a call and ran past its 55 s deadline; and an ask from the previous turn, which clear() deliberately keeps (approvals.rs:79-88). tools::status (tools.rs:143-146) picks the last non-allowed outcome, so the stray 'pending_approval: opening x.example ... call browser_navigate with this URL again later' replaces the current call's own line (for example 'approved: the user allowed y'). It is reachable in practice: the user stops a turn while a card is open, then sends a new message, and the new turn's first browser call is running when the old ask times out. The line names the host, so it misleads the agent but is not a security problem.
- 核对建议：Stamp an ask's outcome with the time the ask started. Keep the start Instant in `Asking` (it is already stored in `asking`), and add `Asking::finish(self, result, asked)` that pushes `Outcome { at: start, .. }` and then unregisters. Use it at gate.rs:477 instead of `record`. outcomes_since(started) then returns only asks that began during this call, which are the ones wait_asks waits for. Asks still in flight at the deadline are still reported through asking_since.

### The oom_score_adj fix writes a fixed 500, which lowers the browser's score (or fails) when the sandbox already runs above 500, and failures are still silent

- 位置：`crates/agent-shim/src/browser/launch.rs:132`；评审定的严重程度：low；核对：不成立
- 场景：OOM_WRAPPER and launch.cjs:11 both write the fixed value 500 and ignore errors. Children inherit the agent's score. If the sandbox already runs above 500 (for example a Kubernetes BestEffort pod at 1000, a Burstable pod at 900+, or a runtime that sets a high score), there are two outcomes. Where oom_score_adj_min is not pinned, the write lowers the browser below the agent. I reproduced this: parent at 900, then uid 65534, dumpable=0, then the sh wrapper; the child read 500. Where runc pinned the minimum, the write fails with EACCES and the browser stays equal to the agent. Either way the kernel no longer prefers killing the browser, and with `2>/dev/null` and `catch {}` nothing is logged. The first review asked for a warning when the write fails. In the default Docker case (inherited 0) the fix works: I checked dash as non-root with a non-dumpable parent, fds 3/4 survive, and Node writes 500.
- 建议：Raise the score relative to the current value and never lower it. In sh: `read a </proc/self/oom_score_adj; a=$((a+500)); [ $a -gt 1000 ] && a=1000; echo $a >/proc/self/oom_score_adj || echo 'thinktin: cannot set oom_score_adj' >&2; exec "$0" "$@"`. Do the same in launch.cjs and write a line to stderr on failure, so it reaches the StderrTail and debug log.
- 核对理由：This only matters if the agent already runs above 500, and none of this project's sandboxes do. The ACS sandbox pod spec (deploy/aliyun/acs.py:300-301) sets cpu/memory requests equal to limits, which is Guaranteed QoS: kubelet/runc give it -997. The local Docker backend sets no --oom-score-adj (no oom setting anywhere in crates/sandbox), so it inherits 0. If envd sets a default score for the processes it starts, that default (about 100 in e2b) is also below 500. In each of these cases, writing 500 raises the score, which an unprivileged process may always do, so the browser and Playwright become the preferred OOM victims as intended. The finder agrees the inherited-0 case works. BestEffort (1000) or Burstable >500 pods are not used. Not logging a failed write is an observability nit, not a defect in any deployment the code ships to.
- 核对建议：None required. Optionally, write max(current, 500) and print one stderr line on failure (it then shows up in the StderrTail and debug log).

## shim-cdp-gate

### pending_main is written inside the spawned on_paused task, so two main-frame pauses arriving together can run out of order and a stale ask result still overwrites the live page's state

- 位置：`crates/agent-shim/src/browser/gate.rs:455`；评审定的严重程度：low；核对：**成立**（low）
- 场景：Gate::run spawns one task per Fetch.requestPaused (gate.rs:253-257). Each task resets pending_main at gate.rs:417-419 and sets it at gate.rs:455-457. The shim uses Runtime::new(), the multi-thread runtime. There, a task spawned from a worker goes into the LIFO slot, and the task spawned before it is pushed to the queue, where another worker can steal it. So when two pauses for one page are dispatched in the same batch, the newer one (B) often runs first. Example: page P is on approved a.com. A script (or a click handler plus the link's default action) navigates to unapproved b.com (R1) and then at once to a.com/next (R2), which cancels R1, and both requestPaused events are read in one pipe chunk. Task B runs first: pending_main=None, Continue, approved=true, continue. Task A then runs: pending_main=None, Ask, pending_main=R1. About 40 s later R1 comes back pending, current is true, and set_approved(false, Some(b.com url)) runs on the page now showing a.com/next. Its lazy loads and XHR hosts are no longer announced and get refused after 3 s, which is the original bug. If instead R2 also asks and A clobbers its pending_main, R2's own pending or denied result is not current: fulfill() runs without setting `explained`, so on_navigated sees the explanation page as an unapproved commit and replaces it with about:blank (gate.rs:585-609). on_navigated also never clears pending_main. A main-frame commit that skips on_paused (about:blank via browser_navigate, a back/forward cache restore) leaves an older paused request marked current.
- 建议：Assign pending_main in Gate::run, synchronously and in event order, before tokio::spawn. For a Fetch.requestPaused that is a Document request on a Page target with frameId == target_id, set targets[session].pending_main = Some(requestId) there. Drop the reset and the set inside on_paused, and keep the after-ask comparison. Also set pending_main = None in on_navigated when the main frame commits.
- 核对理由：Two parts. Both are real and low; the second is the solid one.

(1) The ordering race. I checked the tokio claim with a scratch program on tokio 1.53.2 (`/tmp/claude-0/-home-user-Thinktin-Rust/6eda0341-41b9-5be1-b26f-1c110a526552/scratchpad/lifo`). It mimics Gate::run: one loop that receives two events from an unbounded mpsc in the same poll and spawns one task per event. The second-spawned task ran first in 2000/2000 trials with 1 worker, 1988/2000 with 2 and 1991/2000 with 4. The cause is the LIFO slot. The shim uses Runtime::new() (main.rs:354). on_paused has no await between the reset at gate.rs:417-419 and the set at 455-457. So when two main-frame Document requestPaused events for one session are dequeued in one poll, the older request's task writes pending_main last. That needs both pauses queued at once: the first navigation reaches Fetch interception and a second one starts within the shim's dispatch latency (or while Gate::run is stuck awaiting on_navigated's Page.navigate). That is reachable, but only on unusual pages.

(2) Commits that skip on_paused. This one does not need a race. The shim starts Chromium itself (launch.rs:166-185) and does not pass --disable-back-forward-cache. Playwright passes that flag precisely because the main request is not intercepted on goBack (playwright-core chromiumSwitches.js:57: "Avoids surprises like main request not being intercepted during page.goBack()"). Scenario:
- After call 1 (browser_navigate a.com, approved) returns, a.com's script navigates to unapproved b.com.
- R1 is paused and its ask runs about 40 s with pending_main=R1. No call is in flight, so wait_asks does not cover it.
- The agent calls browser_navigate_back. The earlier approved page comes back from bfcache with no Fetch.requestPaused, so pending_main stays R1.
- on_navigated sets approved=true (it never touches pending_main).
- R1 returns pending or denied. `current` is true (gate.rs:489-495), so set_approved(false, Some(b.com url)) runs on the restored, approved page. Its lazy loads and XHR hosts are no longer announced and are refused after 3 s. That is exactly the original bug.

The about:blank path the finding also names is harmless: the page is already approved=false, and it loads no resources.

Impact stays one document, failing closed, so low.
- 核对建议：Add "--disable-back-forward-cache" to the Chromium args in launch.rs (next to --disable-features, around line 181). Then every main-document commit goes through Fetch.requestPaused, which resets pending_main. Separately, set pending_main in Gate::run (gate.rs:253-257) before tokio::spawn, in event order, for any Document pause on a Page target whose frameId == target_id. Remove the reset and the set from on_paused and keep the after-ask comparison. If you also clear pending_main in on_navigated, do it only for main-frame commits with params.type == "BackForwardCacheRestore". Clearing on every commit wrongly drops a live paused request when an earlier navigation commits after it.

### An ask that outlives its call is recorded with its finish time, so its result still lands as the first line of an unrelated later call

- 位置：`crates/agent-shim/src/browser/gate.rs:477`；评审定的严重程度：low；核对：**成立**（low）
- 场景：BrowserService::call waits for asks only until the 55 s deadline (mod.rs:264), then adds a made-up 'pending' line for asks still running. Approvals::record stamps the real outcome with Instant::now() when the ask finishes (approvals.rs:226-231). outcomes_since(started) filters on that stamp, so the later call that happens to be running then picks it up. Example: on the run's first browser_navigate, ensure() spends ~15-20 s starting Chromium and Node on 1 core. The ask for unapproved b.com starts at ~20 s and runs ~41 s, so call 1 ends at 55 s with the made-up pending line. The agent follows the instruction to do other work and calls browser_navigate(a.com), which is approved. The b.com ask finishes during that call. Call 2's first line becomes 'pending_approval: opening b.com ...', or 'approved: the user allowed b.com', on a navigation to a.com. The same happens with browser_wait_for or slow pages when a script navigates late in the call. The 'lands on an unrelated later call' half of the original finding is still there.
- 建议：Stamp the outcome with the time the ask started, not when it finished. Let Approvals::asking() return its start Instant (or keep it in the Asking guard) and pass it to record() (e.g. a record_at(host, result, asked, at) variant). Call 1, which waited, still sees the outcome, and later calls filter it out because its start is before their `since`.
- 核对理由：Confirmed in code:
- record() stamps Instant::now() when the ask finishes (approvals.rs:221-231), and outcomes_since filters on that stamp (approvals.rs:235-242).
- BrowserService::call (mod.rs:264-276) waits only until its 55 s deadline for asks that started after `started`, then adds a synthetic `pending` for asks still in flight.
- When such an ask finishes later, its real outcome is pushed with the finish time. It is picked up by whatever later call is in flight. That call's wait_asks ignores the ask, because the ask started before the call's `started`, but outcomes_since includes the outcome.

Reachable without odd timing:
- browser_wait_for(time) caps at 30 s (playwright/lib/mcp/browser/tools/wait.js:44). A page-script navigation about 15-20 s into the call starts an ask (up to 40 s plus 2 s) that ends after the call's deadline.
- On the first call, ensure() can take up to START_TIMEOUT=20 s.
- A page-script navigation between calls also lands on the next call that is running when the ask finishes.

tools::status (tools.rs:142-151) picks the last non-allowed outcome first. So a stale 'pending_approval: opening b.com ... call browser_navigate with this URL again later' even replaces the later call's own 'approved: the user allowed c.com' line. The design (section 6) says the first line reports what happened in this call. The cost is a misleading status line only; the line names the other host. So low.
- 核对建议：Stamp ask outcomes with the time the ask started. Keep the start Instant in the Asking guard (Approvals::asking already records Instant::now() at approvals.rs:95), and record through it, e.g. `asking.record(result, asked)` that pushes Outcome { at: start, .. } in place of the record() call at gate.rs:477-481. Explain outcomes keep Instant::now(). A call that waited still sees the result, since start >= its `started`. Later calls filter it out, since start < their `started`.

## proxy-store

### A host-level direct-lane answer still becomes a site-wide browser answer, because the gate widens the proxy's reply

- 位置：`crates/llm-gw/src/egress.rs:1793`；评审定的严重程度：medium；核对：**成立**（medium）
- 场景：Dev mode, one run. The agent runs `curl https://gist.github.com` and the user taps Deny. That stores a direct row: host gist.github.com, site github.com, denied. Later the agent calls browser_navigate("https://gist.github.com/x"). The gate asks the proxy. In ask_inner, site_decision(site=github.com, host=gist.github.com) matches the direct row through the new `host = $5` branch and returns Denied, so the reply is ('denied', None, None). The gate (gate.rs:484-486) calls approvals.deny(host), which denies the whole site github.com (approvals.rs deny inserts site_of(host)). From then on, browser_navigate("https://github.com/...") is refused by the gate itself with the user_denied page, even though github.com is a default dev host and the user never denied it. api.github.com resources are refused by the forward port the same way. Approvals widen too. A curl 'Visit once' for api.example.com, followed by a browser open of api.example.com, returns ('allowed', 'once', None). approve(host, 'once') adds site example.com, so every *.example.com page opens without asking (forward port Grant::Main; the browser lane does not check approvals). The proxy now keeps direct answers host-level, but the reply does not say so, and the gate turns any answer into a site answer. So the problem this fix targets ('a curl denial of one host blocks the whole site in the browser'; design 1.2: direct answers count only for their own URL) still happens once the browser touches that exact host.
- 建议：Have site_decision report whether the deciding row was a browser row (for example return `via` with the status). When the row is a direct one, decide_browser_ask should answer allowed with scope "default", which the gate already records as the exact host only. For a denial it should add a host-only marker (for example scope "host" on 'denied'), and the gate's deny should then go into an exact-host denied set instead of denying site_of(host).
- 核对理由：Confirmed by reading the code. In Dev mode gist.github.com is not in DEV_HOSTS (proto/src/egress.rs:7-18), so a curl to it asks the user. A Deny writes a direct row with site=github.com (the direct lane passes Some(site) at egress.rs:1266-1268). Later the browser opens gist.github.com. gate.rs decide() returns Ask because the gate's Approvals knows nothing about direct answers. In decide_browser_ask, mode.allows and the always check both fail, so ask_inner runs. site_decision(site=github.com, host=gist.github.com) matches the direct row through `via = 'browser' OR host = $5` (store egress.rs, memory ledger :485) and returns Denied, so the reply is ("denied", None, None). The gate (gate.rs:484-486) then calls approvals.deny(host), which inserts site_of(host)=github.com into `denied` (approvals.rs deny). After that, decide() returns user_denied for https://github.com/... (gate.rs:63), and forward.rs:130-133 refuses codeload.github.com and other github.com resources. github.com is a dev default host that the user never denied. The approval side widens the same way: a direct 'once' row for api.example.com makes ask_inner return Ok, decide_browser_ask answers allowed/once, and approve() inserts site example.com. Every *.example.com main page then opens with no card: main_allowed gives Grant::Main, and browser_connect at the proxy only checks denials. docs/browser.md:177 and 1.2 say direct answers count only for their own URL. The original issue therefore still occurs, and the agent pattern that triggers it (curl fails, then try the browser on the same URL) is common.
- 核对建议：Have site_decision say which lane decided, for example return (run, answer, via). Before the fix this lookup succeeded after about 5-10 s. Dropping the future also does not stop the blocking getaddrinfo thread.

- 核对理由：resolve() uses tokio::net::lookup_host, which is getaddrinfo (ssrf.rs:107, egress.rs:1114). llm-gw runs on distroless cc-debian13, so glibc (deploy/docker/Dockerfile:14,46), inside k8s. ### The 40 s budget still leaves out ask_inner's own DB work (site_decision, ledger.ask with the new advisory-lock wait)

### Asks no longer refresh the browser lane's per-minute window, so ask log rows get merged indefinitely after a quiet period

- 核对理由：log() calls may_log(lane_key(instance, Browser)) = "inst#browser" (egress.rs:989-990). may_log (:1070-1077) increments e.2 of the existing entry and never resets an expired window; only attempt() (:1053-1060) resets one.
