# 2.7e 第二轮评审（只看修复 26ee330）原始结果

## store

### [成立] [low] For 60s after an 'always allow', the reused 'always' row lets the agent reach a site the user has just removed

Reproduced on a scratch DB with all migrations applied (/tmp/claude-0/review2-scratch/f1.sql). The steps were: a pending row X inserted as thinktin_llmgw; as thinktin_app with app.user_id set, egress_hosts got x.example.com appended and X set to always; then array_remove left egress_hosts as {}. As thinktin_llmgw, the touch UPDATE then matched 0 rows, and the new reuse SELECT in egress_ask (crates/store/src/egress.rs:261-272) still returned X/always. In Egress::ask (llm-gw/src/egress.rs ~1160-1195), answer(X) goes through Answer::from_status, which maps 'always' to Allowed. handle() then opens the tunnel with approved = ask_user = true. After the wait it re-checks only the token, not allows(). still_allowed() keeps (approved && mode.asks()) tunnels open under dev for the rest of the run. The directory cache is not what lets this through: cache_secs defaults to 5s, and any CONNECT to a host that is not allowed forces a reread. So after a few seconds the new connection reaches the reuse path, and only the 60s reuse window lets it in. After that window the same run would ask the user again, so the behavior inside and outside the window does not match. Removing the site within a minute of tapping 'always' is plausible (for example after a mis-tap), but the window is narrow, so the severity is low. The suggested SQL is wrong: `$2 = ANY((SELECT egress_hosts FROM instances WHERE id = $1))` fails with 'operator does not exist: text = text[]' when $2 is text (checked with PREPARE), because Postgres still parses it as ANY(subquery). Simply dropping 'always' from the reuse would bring back the duplicate-popup race for 'always'.

修法：In the reuse SELECT, keep an 'always' row only while the site is still always-allowed: `AND (status <> 'always' OR EXISTS (SELECT 1 FROM instances i WHERE i.id = $1 AND $2 = ANY(i.egress_hosts)))`. Checked with PREPARE: it returns no row after removal. thinktin_llmgw already has SELECT on instances.

### [成立] [low] egress_ask returns the same None for the hourly cap and the per-task cap, so the agent is told 'wait for those' when nothing is waiting

egress_ask (store/src/egress.rs:278-302) returns None when either condition in the INSERT guard fails. One is the per-run pending count < max_pending (5). The other is the per-instance count of rows created in the last hour, any status, < max_per_hour (20, new in this commit). The memory ledger does the same. Egress::ask (llm-gw/src/egress.rs:1161-1178) turns every None into 403 too_many_asks with 'too many sites are already waiting for the user's approval; wait for those or do it another way'. The agent instructions in bridge.rs do not mention too_many_asks, so this text is the only guidance the agent gets. Realistic case: the user is present and answers each popup ('once' or 'deny' resolves the row). A research task then reaches 20 distinct sites within the hour. The 21st site gets that message while the run has zero pending requests, and no row or popup is created. The agent waits or retries for up to an hour, or tells the user it is waiting for their approval when nothing has been asked. The proxy behavior itself (refusing) is intended; the defect is that the two cases cannot be told apart and the hourly case gets the wrong message.

修法：Have egress_ask (and EgressLedger::ask) return an enum such as Asked(id) / TooManyPending / HourlyLimit. Find out which guard failed with one extra count query when the INSERT returns no row and the retry touch misses. In Egress::ask, send a separate message for HourlyLimit, for example 'too many new sites were asked about this hour; try again later or do it another way'.

### [成立] [low] Pending requests of a deleted instance keep their unread inbox items for up to 24h, and the user can no longer clear them by answering

Confirmed by reading the code. The gateway delete handler (routes/instances.rs:372-392) calls retire_instance_plans, cancel_instance_runs, revoke_instance_grants and delete_instance. None of them touch egress_requests or inbox_items. cancel_instance_runs only bumps epochs and cancels runs. Approvals get settled later through executor cancel_run_approvals, but nothing does the same for egress requests. After this commit, decide_egress_request returns NotFound for a deleted instance, and Tenant egress_requests() hides such rows. The ffi doc says the app finds the request through egress_requests, so it cannot show the prompt, and answering gets a 404. The inbox item stays read_at IS NULL until expire_egress_asks runs (asked_at older than 24h, with no instance filter). unread_inbox_count, the APNs badge, counts it until then. One part of the scenario is overstated: the user can still clear the item with POST /v1/inbox/read. Before this commit nothing marked these items read either, so this is a gap in the new settle-on-answer/expire fix rather than a regression. The effect is cosmetic: a stale prompt that cannot be acted on and an inflated badge for up to a day.

修法：In the gateway delete handler's tenant transaction (or in delete_instance), expire the instance's pending requests and settle their inbox items: `UPDATE egress_requests SET status = 'expired', decided_at = now() WHERE instance_id = $1 AND status = 'pending' RETURNING id`, then `UPDATE inbox_items SET read_at = now() WHERE egress_request_id = ANY($ids) AND read_at IS NULL`. thinktin_app already has UPDATE (status, decided_at) on egress_requests and UPDATE on inbox_items. It must run before delete_instance only if RLS or other checks depend on the instance state; the egress_requests policy is user_id-based, so either order works.

## proxy

### [成立] [medium] The new hourly ask cap counts requests the user already answered and requests from other tasks, and the agent is told sites are 'already waiting' when none are

I reproduced this on a scratch DB with all migrations applied, running the 26ee330 egress_ask statements as thinktin_llmgw in order: touch, decided lookup, guarded INSERT, touch again. One run asked 20 different hosts and each was answered 'once' (status=once, decided_at set), so 0 rows were pending. On the 21st host the per-run pending guard passed (0 < 5). The hourly guard `count(*) ... WHERE instance_id=$1 AND created_at > now()-1h` saw 20 and blocked the INSERT. The retry touch found nothing, so egress_ask returned None. Egress::ask (crates/llm-gw/src/egress.rs ~1173) turns that into 403 too_many_asks, saying 'too many sites are already waiting for the user's approval; wait for those or do it another way'. No row is written, so there is no popup or push, and nothing is actually waiting. MemoryEgressLedger::ask (~line 394) filters only on `a.created.elapsed() < 3600s`, whatever the status, so it behaves the same. Case 1 is more likely than the finding says. 'once' only lasts for one task, so each new task re-asks a host the user already allowed once, and that creates a new row. A user who prefers 'once' and runs 5 short tasks in an hour that each touch 4 sites uses up all 20 slots. After that, no new site gets a popup for the rest of the hour. This breaks the rule that the first time the agent tries a site, the user gets a popup. Case 2 (cross-task blocking) is partly intended: docs/egress.md and the MAX_ASKS_PER_HOUR comment say the cap exists to stop repeated scheduled runs from spamming prompts. It also can't happen with a single run, because the per-run pending cap of 5 limits one unattended run to 5 new rows; it takes several runs in the hour. The core defect does hold: rows the user approved use up the budget, and the reason given to the agent is wrong.

修法：In the egress_ask INSERT guard (crates/store/src/egress.rs ~line 283), stop counting approved rows: `... WHERE instance_id = $1 AND created_at > now() - interval '1 hour' AND status NOT IN ('once','always')) < $7`. Counting 'denied' as well is optional. Apply the same status filter to the `hour` count in MemoryEgressLedger::ask. Also tell the two caps apart, for example by returning an enum from egress_ask or by checking the hourly count again when it returns None. For the hourly cap, give the agent its own reason and message (e.g. `ask_rate`: 'asked the user about too many new sites this hour; try again later or do it another way'), and keep 'wait for those' only for the per-task pending cap.

### [成立] [low] A 'just decided' always row is reused for 60s even after the user removes that site, so new CONNECTs get through without asking

I reproduced this on a scratch DB. I created host H's request, set it to 'always' and appended H to egress_hosts (decide), then ran array_remove(egress_hosts, H) as remove_egress_host does, which left egress_hosts = {}. egress_decision's lookup (once/denied only) returned nothing. The touch matched no pending row. The new decided lookup (`status IN ('once','always','denied') AND decided_at > now()-1 minute AND (status='always' OR run_id IS NOT DISTINCT FROM $3)`) returned the 'always' row for the same run and also for a different, new run, and created no pending row. In PgEgressLedger::answer, 'always' maps to Answer::Allowed. The post-wait check in handle() re-reads the instance and calls verify_token, which looks only at token, epoch and state, not hosts. So the proxy opens the tunnel with Target.approved = true, and still_allowed keeps it alive while mode.asks(), up to max_duration. Before 26ee330, the same CONNECT would have inserted a new pending row and prompted the user. The commit's own store test says it accepts this: 'after a minute (e.g. the user deleted the site in settings) asking again creates a new one'. Even so, every new tunnel to a site the user just removed gets through without asking for up to 60s. That is likely when the user corrects a mistaken 'always' tap while the agent is still actively using H. MemoryEgressLedger has no decided-reuse path, so this affects only the Postgres ledger.

修法：Keep reusing the always row (that is what closes the decide/ask race) only while H is still in the list. Add `AND (status <> 'always' OR EXISTS (SELECT 1 FROM instances WHERE id = $1 AND $2 = ANY(egress_hosts)))` to the decided lookup in egress_ask (crates/store/src/egress.rs ~261-275). thinktin_llmgw already has SELECT on instances. I checked the query as thinktin_llmgw: with H removed it returns nothing (so a new pending row and popup follow), and with H present it returns the always row, so the race fix still works.

## push

### [成立] [low] docs/push.md, the push contract the iOS and Android code cite, still has no egress_request kind, EGRESS_REQUEST category or tt_egress_request key

Confirmed. In 26ee330 the server sends egress asks as the new PushKind::EgressRequest. orchestrator/src/egress.rs builds Notice::new(PushKind::EgressRequest) with egress_request: Some(r.id) and collapse_id egress_request:{id}, and drops the old Info kind and its egress_request subtype. In notify, EgressRequest counts as waits_for_user(), so it gets apns-priority 10 (apns.rs:284 only gives 5 to Info), interruption-level time-sensitive (apns.rs:133), and on FCM HIGH priority on the approval channel (fcm.rs:257-258). outbox.rs im_event maps it to None. The new target key is tt.egress_request on APNs and tt_egress_request on FCM and JPush. Nothing in docs/push.md changed: `git log -- docs/push.md docs/ios.md` ends at 87d56cb, and the later commits beb1b1e and c2b8892 don't touch them. Section 2 still lists 7 kinds. Section 3 still lists only up to tt_vault_request, and its collapse-id sentence covers only approvals, vault requests and plan_confirm. Section 6's auto-mark-read rule doesn't mention egress requests. ios.md 6.1 has no routing rule for the new kind, and it says PushCategory registration follows 'docs/push.md 第 2 节'. The apps treat push.md as the contract. PushPayload.swift says '约定见 docs/push.md 第 3、4 节' and parses only a whitelist of tt keys, with no egress_request among them. PushMessage.kt says 'docs/push.md 第 3 节' and has KEY_* constants only up to KEY_VAULT_REQUEST. InboxKind and PushPayload.Kind don't include egress_request either. An unknown kind falls back to info: iOS routes it run, then conversation, then inbox, with no category actions, and Android puts it on the results channel. An app session working from push.md therefore never registers EGRESS_REQUEST and never parses the request id. The user gets no once / always / deny prompt from the push, and the proxy's 60 s wait runs out. The new kind and keys appear only in egress.md and the ffi.rs doc comments, and the earlier push kind VAULT_REQUEST was added to push.md. The server side works, so severity is low.

修法：docs/push.md section 2: add the row `| egress_request | EGRESS_REQUEST | 10 | time-sensitive | 审批渠道，高 | 否 |` and a bullet: agent 想访问一个网站、代理最多等 60 秒；目标里带 `egress_request`（请求 id，用 `egress_requests` 找、`decide_egress_request` 回答：访问一次 / 一直允许 / 拒绝）. Section 3: add `"egress_request": "…"` to the APNs tt example and `tt_egress_request` to the Android key list, and add 出网请求 to the kinds that carry apns-collapse-id / collapse_key. Section 6: add that the egress inbox item is marked read once the request is answered or expires. docs/ios.md 6.1: add a routing rule for kind `egress_request` (open the egress prompt for the request id; without an id, the instance's pending list, then the inbox item). Also add `egress_request` to the 6.1 list of tt keys PushPayload parses.
