# 2.7e 评审原始结果（2026-11-04，4 个方面，每个方面一个反驳者）

## security

### [成立] [medium] api.tavily.com in the default SEARCH_HOSTS fetches arbitrary pages, which bypasses the per-site approval

In crates/proto/src/domain.rs:564-571, `EgressMode::Dev.allows()` returns true for any host in `SEARCH_HOSTS`. Since migration 0034, Dev is the default for every instance and every existing instance. In Egress::handle (crates/llm-gw/src/egress.rs:910), an allowed host skips ask() entirely: no request row, no notification. `api.tavily.com` is on the list (crates/proto/src/egress.rs:38). Tavily's public API on that same host has POST /extract, which takes a list of arbitrary URLs and returns each page's full content. It also has /crawl and /map, and /search can return raw page content with include_raw_content. So an agent with any Tavily key (the user's own, or a free-tier key planted by a prompt injection) can read any website through one CONNECT to api.tavily.com, and the user is never asked. That breaks the founder's rule that any other website gets a popup the first time. It also breaks the code's own invariant: the doc comment above SEARCH_HOSTS and docs/egress.md:108 both say services that fetch arbitrary pages for you (r.jina.ai, translation proxies) are left out because they bypass per-site approval. Nothing else in the code limits which Tavily paths can be used, because the proxy only sees the CONNECT host. Internal addresses are not exposed, since Tavily fetches from its own network. The exfiltration angle is also not new, because DEV_HOSTS such as github.com already allow it. What this does add is reading arbitrary sites without a prompt, which is the very thing this change is meant to gate. I checked the other SEARCH_HOSTS entries (the Google, Bing, DDG, Baidu, Sogou and so.com search pages, and api.search.brave.com) and none of them is a general URL fetcher the way Tavily /extract is.

修法：Remove "api.tavily.com" from SEARCH_HOSTS and drop Tavily from the list in docs/egress.md. If Tavily search must work without a popup, expose it through a gateway-side search tool that only calls /search, with raw content off. A raw CONNECT allow for this host cannot be made safe.

### [成立] [medium] Stale pending requests from finished tasks fill the 5-site cap for 24h, so later tasks get too_many_asks and the user is never asked

crates/store/src/egress.rs:270-273 only INSERTs a new request while `(SELECT count(*) FROM egress_requests WHERE instance_id = $1 AND status = 'pending') < $6`. That counts every pending row on the instance, whatever run it belongs to. Pending rows only leave that state in three ways: the user answers (decide_egress_request), the 24h expiry in maintain (expire_egress_asks with asked_at < now - 24h, workers.rs EGRESS_ASK_EXPIRY_HOURS), or purge. Nothing expires or discounts them when their run ends; grep shows no other writer of egress_requests. Each re-ask also resets asked_at (touch_request!). Concrete failure: task R1 tries 5 unlisted sites while the user is away. Each gets a pending_approval 403 after 60s, which is the behavior the product rules expect, and R1 ends. Within the next 24h, task R2 needs a new site H. The UPDATE finds no pending row for H, the INSERT's WHERE filters out the row (count=5), and egress_ask returns None. Egress::ask (egress.rs:1076-1092) then returns 403 too_many_asks. No row is created and notify_requests sends nothing, so the user is never asked about H and R2 cannot get H approved however long it waits. The user can only unblock it by finding and answering R1's stale requests in the app, or by waiting 24h. This contradicts the rule that the first time the agent tries a site, the user gets a popup. The cap is meant to stop one agent firing many prompts at once, not to block later tasks.

修法：Count only pending requests of the current run toward MAX_PENDING_ASKS by adding `AND run_id IS NOT DISTINCT FROM $3` to the count subquery. Alternatively, mark a run's pending egress_requests as expired when the run reaches a terminal state, or exclude pending rows whose run is terminal from the count.

### [成立] [low] An approval that arrives during the up-to-60s wait opens the tunnel without re-checking the token, so a cancelled or ended run's process still gets through

Egress::handle calls gw.verify_token once (egress.rs:874), before ask(). ask() then polls only ledger.answer(id), for up to ask_wait (60s). On Answer::Allowed, handle goes on to wait_slot (up to another 30s), reserve, resolve and connect, then returns 200, and the token is never checked again. Inside tunnel(), the first tick of `interval(recheck_every)` is consumed before the loop, so the first still_allowed() runs 30s after the tunnel opens. The 5s directory cache TTL (main.rs cache_secs) is not the bottleneck, and verify_token force-refreshes when it sees an epoch mismatch, so that recheck does catch the stale epoch. Scenario: a process from run R1, such as a background job the agent started, CONNECTs to an unlisted host and waits. R1 is cancelled or finishes, which bumps the epoch, or the grant is revoked. The user then taps 'allow once' on the popup that is still showing; the request is R1's, or R2's if R2 re-asked the same host. The waiting connection sees Allowed and opens a tunnel for a token that is already invalid, and it stays open until the next recheck (about 30s). A later CONNECT with that token gets a 407, so exposure is capped at one tunnel for about 30s to a host the user just approved. That is real but minor. The old path had the same 30s wait_slot gap; this change makes the unchecked window longer and ties it to a user action that can happen after the run ended.

修法：After ask() returns Ok (and after wait_slot), call `self.gw.verify_token(&token, peer).await` again and refuse with 407 auth if it fails. Before treating Allowed as valid, the wait loop can also check that the request's run is still the instance's current run.

## state

### [成立] [medium] Pending cap counts stale asks from finished runs, so a new site cannot get a popup for up to 24h

Confirmed in a1ed4ec crates/store/src/egress.rs:272. The cap check is `count(*) ... WHERE instance_id=$1 AND status='pending'` and ignores run_id. No code expires or closes pending rows when a run ends: the only writers of status are decide_egress_request and expire_egress_asks, which uses `asked_at < now()-24h` (workers.rs EGRESS_ASK_EXPIRY_HOURS=24, checked once per maintenance tick). Each touch also refreshes asked_at. Egress::ask (llm-gw/src/egress.rs:1075-1094) turns a None into 403 too_many_asks and makes no ask, so the user is never notified. Scenario: a nightly scheduled run R1 hits 5 unlisted sites while the user sleeps. At 8am an interactive run R2 needs site Y, and the agent gets an immediate too_many_asks with no popup. That breaks the rule that every other site gets a popup the first time. A recurring task that retries any of the 5 hosts keeps the lockout going past 24h. The cap's own comment says its purpose is only to stop one burst of prompts ('一口气弹一堆提示'). Workaround: the user answers or denies the old 5 first, but nothing tells them about Y.

修法：Count only pending rows that belong to the current run (or have no run): add `AND run_id IS NOT DISTINCT FROM $3` to the count subquery. Alternatively count only rows asked within the last few minutes, or expire pending rows whose run has ended.

### [成立] [low] expire_egress_asks can overwrite a decision the user just made (or an ask just refreshed) with 'expired'

Reproduced on the local PG16 in a scratch DB. Session A ran SELECT FOR UPDATE, then UPDATE status='once', then slept 3s before COMMIT. Meanwhile the expiry statement from egress.rs:454 (`UPDATE ... SET status='expired' WHERE id IN (SELECT id ... WHERE status='pending' AND asked_at < $1 LIMIT $2)`) waited on the lock and then reported UPDATE 1. The final row was status='expired' with decided_at set. The LIMIT subquery is not re-checked by EvalPlanQual, only the outer id match is. Effect: a 'once' or 'deny' answer is lost. The waiting proxy sees Gone and returns pending_approval, and the next retry in the same run opens a new popup. ('always' still works because egress_hosts was already appended.) The same happens to a touch that refreshes asked_at. The window is very small: a decision on a pending row more than 24h old has to commit during a maintenance tick.

修法：Repeat the predicate on the target row: `UPDATE egress_requests SET status='expired' WHERE status='pending' AND asked_at < $1 AND id IN (SELECT ...)`. I verified this updates 0 rows and leaves 'once' in place. Alternatively add FOR UPDATE SKIP LOCKED to the subquery.

### [成立] [low] Concurrent asks for the same new host at the cap: the loser gets too_many_asks although the host now has a pending row

Reproduced with 4 pending rows and a cap of 5. Session A ran the INSERT...SELECT...WHERE count<5 ON CONFLICT statement and held it uncommitted. Session B's touch UPDATE returned 0 rows. After A committed, B's INSERT returned `INSERT 0 0` with no id. The guard proposed no row, so ON CONFLICT never fired, and egress_ask returned None, which Egress::ask turns into 403 too_many_asks. This needs the instance to be exactly one below the cap, plus two connections to the same new host whose touch/insert gap (a few ms) overlaps the other's insert commit. Impact: one connection gets a misleading 'too many sites waiting' message while the other waits on the new ask.

修法：When the INSERT returns no row, run the touch UPDATE once more and return its id if it finds one. Or make the guard `WHERE count < $6 OR EXISTS (SELECT 1 FROM egress_requests WHERE instance_id=$1 AND host=$2 AND status='pending')`.

### [成立] [low] A decision committed between the proxy's decision lookup and its ask creates a duplicate pending request and a second popup

Code path confirmed. handle() re-reads the directory (egress.rs:917), then Egress::ask calls ledger.decision() (PgEgressLedger: egress_current_run + egress_decision, which only matches 'once'/'denied') and then ledger.ask() (egress_ask, whose touch only matches status='pending'). These are separate statements and transactions. If the user's decide commits after B's fresh read or decision() and before B's touch, the touch finds nothing (under READ COMMITTED a blocked touch re-checks status and skips the row), and the INSERT creates a new pending X2 that the worker notifies within about 2s. B waits 60s on X2 and returns pending_approval. Later retries are allowed through the 'once' row or egress_hosts and never touch X2. X2 stays as a stale popup, counts against the cap for 24h, and if tapped 'deny' it becomes the newest decision for the run and blocks the host. The window is only a few ms, so this is rare.

修法：In egress_ask, when the touch misses, check in the same statement or transaction whether a once/denied row for this run, or an always row for this instance and host, was decided recently (or whether the host is already in instances.egress_hosts). If so, return that row instead of inserting.

### [成立] [low] Answered requests are purged by created_at, not decided_at, so a fresh 'deny' or 'once' can be deleted right away

Confirmed at egress.rs:487-493: `DELETE ... WHERE status <> 'pending' AND created_at < usage_before(=today-60d)`. created_at never changes, while touches keep a pending row alive indefinitely: asked_at is refreshed and expiry uses asked_at. A row kept pending for more than 60 days (for example an hourly scheduled task the user never answers, with push muted) is deleted at the next maintenance tick once the user decides. Later connections to the host in the same run then find no decision and ask again. The logic is clearly wrong, but the precondition (more than 60 days of ignored, repeatedly refreshed asks) is very unlikely.

修法：Purge on the decision time: `status <> 'pending' AND coalesce(decided_at, asked_at) < $1`.

### [驳回] [low] 'Always allow' append can be silently lost to PATCH /v1/instances, which replaces the whole hosts list

update_instance (crates/store/src/instances.rs) is not changed in 90d2dc5..a1ed4ec. Its full-list `egress_hosts = coalesce($6, egress_hosts)` replace without a version check is pre-existing, and two devices editing the list already had the same lost-update problem. The new decide(Always) path is itself atomic and correct: it appends with an ANY() check and cap in a single UPDATE under the request's FOR UPDATE lock. Losing the host needs a client that edits a hosts copy loaded before the decide and does not refresh after it. That is client behaviour the reviewed backend code does not control, and the result fails closed (the user is just asked again). This is a general concurrency limitation, not a defect introduced by this change.

修法：Optional hardening, not required for this change: add optimistic concurrency (if-match on updated_at) or add/remove deltas to PATCH egress, and have clients refetch the egress view after deciding.

## proxy

### [成立] [medium] Pending requests from finished tasks hold the 5-site cap for up to 24h, so new sites get too_many_asks and the user is never asked

Confirmed. In egress_ask (crates/store/src/egress.rs:269-276), the insert guard counts every pending row of the instance (`count(*) ... WHERE instance_id = $1 AND status = 'pending'`) whatever its run_id. Nothing moves a request out of 'pending' when its run ends: grep finds no egress_requests reference in runs.rs, and bump_epochs_where does not touch the table. Only expire_egress_asks does, 24h after asked_at, and touch_request refreshes asked_at on every retry. I tested this on a scratch DB with all migrations applied. Run b01 (running) asked a..e.example and got 5 pending rows. I then set b01 to succeeded and started run b02. The same INSERT for f.example under b02 returned 0 rows, and the 5 b01 rows stayed pending. In Egress::ask, None becomes 403 too_many_asks. No request row is created, so the worker sends no popup or push for the new site. The agent is told to 'wait for those', but the user is no longer asked about them. This breaks 'first time the agent tries a site, the user gets a popup' for up to a day after the user ignores 5 prompts, for example during overnight scheduled tasks.

修法：In egress_ask, make the cap count only this task's pending requests: add `AND run_id IS NOT DISTINCT FROM $3` to the count subquery, or only recently asked ones (`AND asked_at > now() - interval '10 minutes'`). Or mark a run's pending egress_requests 'expired' in the same transaction that ends the run.

### [成立] [low] Decision/ask race: a parallel CONNECT right after the user answers creates a second popup (even after 拒绝) and fails with pending_approval

Confirmed, but the window is narrow. Egress::ask calls ledger.decision() and ledger.ask() in separate transactions (pg.rs decision/ask). For 'always', the forced directory read in handle() comes before both. egress_ask's touch UPDATE and its ON CONFLICT only match status='pending', and the unique index is partial on pending. So if decide_egress_request commits between a connection's decision()/directory read and its ask(), a fresh pending row is inserted. I reproduced this on a scratch DB: create R pending, decision query returns nothing, set R to 'denied', then the touch UPDATE affects 0 rows, the INSERT creates R2 pending with notified_at NULL, and the worker would push it again. That connection then waits 60s on R2 and returns pending_approval. After 拒绝 this re-asks the user within the same task. After 一直允许, R2 holds a pending slot until expiry, because later CONNECTs pass allows() and never touch R2. The window is a few DB round trips (milliseconds) and needs a new CONNECT to that host to land in it. Clients that already wait in the poll loop are fine. It is plausible with a tool hammering the host, but rare, so low.

修法：After ask() returns an id, re-run ledger.decision() (and, for 'always', the forced directory read) before waiting, and honor an answer found there. Or, in egress_ask before inserting, return early if the same run has a once/denied row for the host, or there is an 'always' row decided in the last few seconds.

### [成立] [low] Token and run are not re-verified after the up-to-60s approval wait (plus 30s slot wait), so a tunnel can open for a run that already ended

Confirmed. handle() calls verify_token once, at the start. After `self.ask(&caller, &host).await` returns Ok, which can take up to ask_wait=60s, it goes through wait_slot (up to 30s), reserve, resolve, connect and spawn tunnel with no re-verification. In tunnel(), `recheck.tick().await` consumes the immediate first tick, so the first still_allowed check comes only after recheck_every=30s. Scenario: a background process from an ended run attempt (the case bump_epochs_where exists to cut off, per its comment in runs.rs) is waiting on an unapproved host. The run ends and the epoch is bumped. The user then taps 访问一次 on the still-pending popup within the minute. The stale-token connection gets 200 and moves data for up to 30s, against 'once is for the current task only' and docs item 5 ('任务结束（令牌代数变了）照样断'). Impact is limited: the host is one the user just approved, and the pre-existing slot wait already had a 30s gap, but this change widens the gap to 90s. The second claim, that the ignored forced read lets a stale token pass, only applies while the cached directory entry still has the old epoch (within the cache TTL), so it is marginal.

修法：After ask() returns Ok (and after wait_slot), call `self.gw.verify_token(&token, peer).await` again and refuse with auth if it fails. Optionally also apply the same usable() test (active, sandbox, epoch == claims.ep) to the `fresh` instance from the forced read before asking.

### [成立] [low] CONNECTs the client abandons during the approval wait are never written to the access log or counted in metrics

Confirmed. The egress listener builds hyper http1 with keep_alive(false) and with_upgrades(), and never enables half_close. In hyper 1.12, after a CONNECT head with zero-length body, reading is Reading::KeepAlive, so is_mid_message() is true. poll_read_keep_alive then calls mid_message_detect_eof, which returns Err(incomplete) on client EOF. Dispatcher::poll_loop propagates it with `?` and drops the in-flight service future. That drops handle() while it is inside Egress::ask, and record_denial (which writes the egress_log row and increments thinktin_egress_tunnels_total) only runs after ask() returns. pip's default 15s timeout covers the CONNECT response (urllib3 runs _tunnel inside connect), so pip gives up well before 60s; docs item 6 itself notes this. For such clients, repeated attempts at an unapproved site leave no egress_log row and no metric. Only egress_requests (and thinktin_egress_asks_total) record them, and purge_egress deletes decided or expired requests after 60 days, so the 6-month log has no trace of them. No bytes move, so the impact is limited to audit and the App's recent-denied list.

修法：Hold a small guard across ask() (and wait_slot) that, if dropped without being disarmed, logs a denial with reason 'pending_approval' or 'client_gone' and increments the counter. The log call runs in a spawned task, as record_denial already does.

### [成立] [low] User is prompted even when today's allowance is already used up; after approving, the agent still gets 429 quota

Confirmed ordering. In handle(), the allows()/ask() step (up to 60s, plus a registered request and a push) comes before wait_slot and ledger.reserve(). When reserve returns 0, the response is 429 quota. Scenario: an instance has used its 100 MiB for the day and the agent tries several unlisted sites. Each one creates a request and a push or popup, and the agent waits up to 60s. If the user doesn't answer, the agent gets pending_approval ('do other work first and retry later'), which is misleading because nothing can connect today. If the user taps 访问一次, the retry still fails with 429 quota, and the approval is wasted if the run ends before the Beijing-time day rolls over. 一直允许 still has value for later days, so the impact is user annoyance plus a misleading agent message. Low.

修法：Before calling ask(), do a cheap read-only check of today's usage against daily_bytes, or a reserve(…, 0-or-small) probe, and return 429 quota without registering a request. Keep DNS resolution after approval.

## api

### [成立] [medium] Website-approval prompt goes out as a low-priority generic Info push, so the 1-minute wait often runs out before the user sees it

Confirmed. orchestrator/src/egress.rs builds `Notice::new(PushKind::Info, ...)`. In notify/src/lib.rs, `waits_for_user()` is only Approval/ComputerApproval/VaultRequest, so Info gets: apns.rs:283 `apns-priority` "5", no `interruption-level: time-sensitive` (apns.rs:133); fcm.rs:256-260 and jpush.rs:120-130 NORMAL/0 priority on `default_channel`; iOS category "INFO" (shared with every other Info notice). outbox.rs:65-73 `im_event(Info)` is None, so the module doc's "订了 IM 的也发" is wrong. The codebase's own rule for `waits_for_user` is "运行停下来等用户 → time-sensitive, approval channel, high priority", and here a CONNECT is held for 60 s waiting on the user. A locked or idle phone, or one in a Focus mode, gets the prompt late or silently. The agent then gets pending_approval even when the user would have answered at once. The designed fallback (retry later) still works, so nothing is lost, but the founder's 1-minute wait is often wasted.

修法：Add an urgent kind for egress asks, e.g. PushKind::EgressRequest. Include it in waits_for_user(), give it its own category ("EGRESS_REQUEST") so the app can register once/always/deny actions, and add a migration if inbox kind is CHECK-constrained. Use it in notify_requests. Fix the module doc that says IM subscribers are notified.

### [成立] [medium] Unanswered requests from finished tasks keep counting toward the 5-pending limit for 24 h, so new sites are refused without asking the user

Confirmed by reading store/src/egress.rs. egress_ask's INSERT is guarded by `(SELECT count(*) FROM egress_requests WHERE instance_id = $1 AND status = 'pending') < $6`, which counts pending rows from any run. The only code that moves pending rows out of 'pending' is decide_egress_request and expire_egress_asks (`asked_at < now-24h`, from workers.rs maintain). `git grep egress_requests` shows nothing touches them when a run ends. Scenario: in R1 a research agent tries 5 unlisted hosts from search results while the user is away, and R1 ends. Within 24 h, R2 tries a new host: egress_ask returns None, the proxy returns 403 too_many_asks, and no row is created, so no push is sent. Answering a stale R1 prompt with 'once' or 'deny' also does nothing for R2: egress_decision matches `run_id = $3`, so R2 asks again.

修法：Count only pending rows of the current run toward the limit (e.g. add `AND (run_id IS NOT DISTINCT FROM $3 OR asked_at > now() - interval '1 hour')` to the count). Or, when a run reaches a terminal state, detach or expire its pending rows. 'always' answers on stale rows are still useful, so detaching is better than deleting.

### [成立] [low] Inbox items for egress requests are never marked read when the request is answered or expires, so the unread badge keeps growing

Confirmed. notify() inserts an unread inbox item for every claimed ask, and the dedupe key `egress_request:{id}:{run}` gives each re-ask in a new run a new item. The APNs badge is unread_inbox_count (read_at IS NULL). decide_egress_request and expire_egress_asks never touch inbox_items. Approvals (approvals.rs:160/194, settle_approval_inbox) and vault requests (settle_vault_request_inbox) clear their prompts on the server. A user who answers from the instance's pending list (GET /v1/instances/{id}/egress `pending`) or on another device keeps a stale unread 'allow once, always, or deny?' item. The push does carry inbox_id, so an app that answers from a tapped push could mark it read itself. The effect is badge and inbox clutter, not a broken flow, so I lowered the severity from medium.

修法：In decide_egress_request (Tenant tx; thinktin_app can already update read_at) and in expire_egress_asks, run `UPDATE inbox_items SET read_at = now() WHERE dedupe_key LIKE 'egress_request:' || $1 || ':%' AND read_at IS NULL`. Or add an egress_request_id column the way vault_request_id was added.

### [成立] [low] The push and inbox item don't carry the request id, so the app cannot open the one request a notification is about

Confirmed. Notice in orchestrator/src/egress.rs sets only instance, run, subtype, dedupe_key and collapse_id. PushTarget (notify/src/lib.rs:125) has instance_id/run_id/approval_id/plan_id/inbox_id/vault_request_id and no egress request id, and the host appears only in the localized body. Up to 5 requests can be pending for the same instance and run with identical structured data. A notification action (once/always/deny on the push) has no id to POST to /v1/egress-requests/{id}/decide. A 'pick the newest pending' heuristic picks the wrong one when the push is a re-notification of an older request (the touch_request path). The app can still show all pending requests for the instance, which is why this stays low.

修法：Add an egress request id (and host) to Notice/PushTarget and the inbox item (an egress_request_id field like vault_request_id), set it in notify_requests, and document it in the ffi EgressRequest doc.

### [成立] [low] Agent INSTRUCTIONS always say search and developer sites work through the proxy, even when no proxy is configured or the instance is not on 'dev'

Confirmed. bridge.rs `INSTRUCTIONS` is a const returned in every MCP initialize from run_client, which has no knowledge of THINKTIN_EGRESS_PROXY. The orchestrator (exec.rs:194) sets that env only when `[sandbox] egress_proxy` is configured, and only deploy/k8s/overlays/tokyo/server.toml sets it; the production and staging server.toml do not. Agents there have no internet at all, but are told web search and package registries 'work directly' through the platform proxy. The harm is limited: without a proxy they see connection failures, not 403 pending_approval, so they won't claim to be waiting for an approval. They do waste effort and may misinform the user that search is available. Custom and model modes are also described wrongly, but no app path sets them now.

修法：Include the egress paragraph only when the agent actually has the proxy, e.g. check the proxy env var (HTTPS_PROXY / THINKTIN_EGRESS_PROXY) in the MCP process or pass a flag to run_client. Word it so it doesn't promise direct access for every tier.

### [成立] [low] Pending requests of a deleted instance stay listed, and answering 'always' returns a misleading 'already has 50 sites' 422

Confirmed. The gateway delete handler calls retire_instance_plans, cancel_instance_runs, revoke_instance_grants and delete_instance (a soft `state = 'deleted'`, instances.rs:372), and none of them touch egress_requests. Tenant egress_requests() filters only on instance_id/status, so GET /v1/egress-requests still lists the prompt. In decide_egress_request, 'always' runs `UPDATE instances ... WHERE id = $1 AND state <> 'deleted' AND (...)`, which affects 0 rows and maps to Error::Invalid "the agent already has 50 always-allowed sites; remove one first" (422). The row stays pending until the 24 h expiry. 'once' and 'deny' quietly succeed with no effect.

修法：In decide_egress_request, check the instance first and return NotFound or Conflict when it is deleted, separate from the list-full case. Also expire the instance's pending egress_requests in delete_instance (or filter by a live instance in egress_requests).

### [成立] [low] 'Always allow' appends to egress_hosts while the settings screen replaces the whole list, so a stale settings save silently removes the new site

Confirmed lost update. gateway instances.rs update → egress_change → update_instance replaces egress_hosts with the request's list. The ffi set_instance_egress doc tells the app to pass the instance's current mode and the trimmed list. decide_egress_request(Always) appends to egress_hosts in a separate transaction. The sequence 'settings loaded [a,b] → popup → always c (now [a,b,c]) → user removes b and saves [a]' drops c without warning. This change adds a second writer that fires while the user is mid-task, which makes the race plausible. The only cost is a repeat prompt for c, so it stays low.

修法：Add single-host add/remove operations (e.g. DELETE /v1/instances/{id}/egress/hosts/{host}) for the settings screen, or make the PATCH take the expected previous list or version and return 409 on mismatch.

### [驳回] [low] Instance.egress_mode now decodes as 'dev' when an old server sends no egress_mode, although such servers have no internet access

Not a realistic failure. A missing egress_mode only happens against a pre-2.7 server. That server also lacks /v1/instances/{id}/egress and /v1/egress-requests, so the app's egress UI fails there anyway, and with no tier switch in the app, nothing acts on the decoded value. Servers on this change always send egress_mode, and migration 0034 sets the DB default to 'dev'. Unknown values still map to Model via lenient_egress_mode. The llm-gw DevStore default only affects local development (MemoryEgressLedger), where the new default matches the product default.
