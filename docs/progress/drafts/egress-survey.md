# 出口代理（WBS 2.7）调研

## 摘要

I surveyed the code and docs for everything a controlled internet channel (egress proxy, WBS 2.7) has to fit. Nothing for it is built yet. docs/egress.md is planned but does not exist. These are the constraints it must respect.

(1) Networking per backend. ACS creates every sandbox with allow_internet_access=false, plus an allowOut list of IP, CIDR or domain entries. The list has no port and no wildcard, so allowing an address opens all its ports. Ports are limited only by the security group on the service machine. Today the list is one global config value (only the service machine IP, 10.0.1.10). It is not per template, and there is no NAT. Cube does the same but drops ports, and its sandboxes go out through node SNAT, so the gateway cannot tell sandboxes apart. Cube's traffic tokens are for inbound data-plane calls (envd), not for egress. The local backend has no network isolation at all.

(2) Identity. The only credential inside a sandbox is the sandbox token, in the env var THINKTIN_SANDBOX_TOKEN. It is an Ed25519-signed tts1 token. Its claims are the instance, user, run grant, sandbox id, `net` (the source IP the gateway must see) and `ep` (token_epoch). It is issued per run from the run grant, lasts at most 24 h, and becomes invalid when an attempt ends (the epoch is bumped). llm-gw checks the signature, then that the TCP peer IP equals `net`, then the current sandbox id, the epoch, that the instance is running, and that the grant is not revoked. That check needs the sandbox to connect to the gateway directly, with no SNAT or proxy in between. This is why llm-gw runs with hostNetwork on the service machine.

(3) llm-gw already has the strict SSRF code a proxy needs. It is https-only and rejects any address that is not public, including 10/8, 172.16/12, 192.168/16, 100.64/10 (which covers Alibaba's 100.100.100.200) and 169.254/16. It resolves and checks DNS in the same step as connecting, and it does not follow redirects. Its --egress-proxy option exists but is not used in deployment. When it is set, DNS-rebinding protection becomes the proxy's job.

(4) Vault. Credential injection by the egress proxy is explicitly deferred to 2.7. The Scrubber removes vault values only from logs and from model requests. Values sent out to the internet are left to the egress allowlist.

(5) Plans. The architecture wants: deny internal addresses and metadata by default, a policy per template, model traffic only through llm-gw, credentials injected by the proxy, the platform paying for web traffic with a per-instance rate limit, and caps on CPU and egress to prevent abuse. The threat model lists the egress allowlist and the metadata block as the top pre-launch todo.

(6) Env. agent-shim builds each agent's env from scratch but passes through HTTP(S)_PROXY, NO_PROXY, SSL_CERT_FILE, NODE_EXTRA_CA_CERTS, REQUESTS_CA_BUNDLE and CURL_CA_BUNDLE. A code comment says these exist because egress will go through a proxy that issues certificates. Nothing sets them today: not the orchestrator, not the image. There is no NODE_USE_ENV_PROXY, so Node's built-in fetch would ignore the proxy settings.

(7) The agents are audited to need only the model gateway. One exception: OpenClaw fetches ClawHub on a hard-coded address, and the egress policy is expected to block it.

(8) Grants and policies have no network fields. GrantScope has only aliases, platform_tools and max_tokens. Approvals use the ACP tool kinds the agent reports itself, such as `fetch`. They express the user's intent and are not a security boundary.

(9) Recording. The usage_records table is specific to model calls. audit_log, events (strings over 16 KiB are cut) and Prometheus metrics exist, and egress would need its own usage table.

(10) Tests. Network blocking is tested only against mock create-request bodies and with unit tests (rule validation, SSRF ranges, token and source-IP checks), plus offline/strace smoke tests run on a dev machine. Real ACS checks are written in deploy/aliyun/sandbox.py but have not been run: metadata 100.100.100.200 unreachable, vendors unreachable, and two sandboxes unable to reach each other.

## 事实（带出处）

- The sandbox egress policy type is just a list of `host:port` allow targets, documented as default deny with only the listed targets allowed (usually just the model gateway)（crates/sandbox/src/lib.rs:61-66）
- SandboxInfo.address is the source address the model gateway sees, the sandbox token is bound to it, and it may change after resume（crates/sandbox/src/lib.rs:86-88）
- The SandboxProvider trait has only create/get/exec/pause/resume/snapshot/restore/destroy/file I/O, with no network or port operations（crates/sandbox/src/lib.rs:161-231）
- ACS create sends allow_internet_access=false and, only if the list is non-empty, network.allowOut=[hosts]（crates/sandbox/src/acs.rs:367-377）
- ACS allowOut accepts only IP, CIDR or lowercase domain, with no port, wildcard, scheme or single-label host. A port would be misleading because sandbox-manager does not filter by port and the whole machine is opened. Bad rules are rejected before any request（crates/sandbox/src/acs.rs:137-165; crates/sandbox/src/acs.rs:343-347）
- The ACS doc says allowOut has no wildcard and no port, so allowing an address allows all its ports. The gateway is allowed by IP and its port is restricted by the service machine's security group. ACS pods must not share that security group（docs/sandbox-acs.md:13; docs/sandbox-acs.md:83）
- In-cluster traffic (sandbox-manager, envd, model gateway) is plaintext HTTP, so tokens cross the VPC in clear. This is accepted for the 10-user test（docs/sandbox-acs.md:84）
- Each ACS sandbox is a Pod whose egress is not SNATed, so the model gateway sees the Pod IP. The IP comes from sandbox-manager metadata (e2b.agents.kruise.io/sandbox-ip), never from inside the sandbox. Creation fails if no IP arrives within ip_wait. Nothing between sandbox and gateway may NAT or reverse-proxy（docs/sandbox-acs.md:64-73; crates/sandbox/src/acs.rs:15-16,44-46,186-194）
- Not yet verified on ACS: that sandboxes reach only the gateway and cannot reach 100.100.100.200 or other sandboxes, and whether the gateway peer really is the Pod IP（docs/sandbox-acs.md:116-121）

## 结论

- Placement: the cheapest proxy location is on the service machine, next to llm-gw with hostNetwork. ACS allowOut already permits that IP on every port, so it only needs a new security-group port. It would reuse the machine's public EIP, which means one shared Tokyo exit IP and per-GB outbound billing. No NAT gateway is needed.
- Identity: the proxy can reuse llm-gw's exact auth chain. A token in Proxy-Authorization, built from THINKTIN_SANDBOX_TOKEN at launch, is checked for signature, net equal to TCP peer IP, current sandbox, epoch, running state and unrevoked grant. That requires a direct sandbox-to-proxy TCP path with no SNAT or LB, as for llm-gw. A lighter alternative is identity by source IP alone (instances.sandbox_address), but that has no index or uniqueness and is exposed to Pod IP reuse.
- Because the epoch is bumped when each attempt ends, a token-checked proxy cuts off egress for background processes (e.g. a browser left running) between runs. Either decide that this is the intended behavior or design a separate long-lived browser credential.
- NO_PROXY must include the gateway IP (10.0.1.10, or the gateway host). If model traffic goes through the proxy, llm-gw sees the proxy as the peer and every token is rejected.
- Proxy env must be added explicitly. The orchestrator sets only THINKTIN_SANDBOX_TOKEN and the image sets no proxy vars. The natural place is agent-shim render() (per agent) or the ExecSpec env. Node 24's built-in fetch needs NODE_USE_ENV_PROXY=1 (or an agent-specific setting) to honor HTTPS_PROXY. Other runtimes (Python requests, curl, git, npm, pip) read the standard vars.
- TLS interception (MITM) for header injection or URL-level filtering needs a CA in the image plus SSL_CERT_FILE / NODE_EXTRA_CA_CERTS / REQUESTS_CA_BUNDLE / CURL_CA_BUNDLE. The shim already passes these through. A CONNECT-only proxy (filter on SNI or host) needs no CA but cannot inject vault headers.
- The proxy must reimplement the SSRF rules of ssrf.rs (or reuse the crate): deny RFC1918, 100.64/10 (100.100.100.200), 169.254/16 and IPv6 non-global addresses; resolve and connect in one step; pin the resolved IP. It must also explicitly deny the VPC CIDRs and the service machine itself, because the SG opens 80/443/8790 there. Without this a sandbox could reach RDS, sandbox-manager or other sandboxes through the proxy.
- Today's single global network_allow does not fit the planned per-template policy. That needs a manifest [network] or policy field, or an instance/grant-level egress scope. GrantScope and PlanPolicy have no network fields, so options are a new GrantScope field (which children can only narrow, like aliases) and a per-instance on/off switch.
- Approvals cannot gate egress safely, because ACP kinds such as `fetch` are self-reported. Enforcement has to live in the proxy. Approvals or risk tiers (like computer_* ReadOnly/Normal/High) can only add user intent on top.
- Metering: usage_records is LLM-shaped, so egress needs its own table (e.g. egress_usage: instance, user, grant, sandbox, jti, host, bytes up/down, decision). Proxy denials can go to audit_log (actor agent:<instance>) and/or an instance event (e.g. egress.blocked), with strings kept under 16 KiB. Per-instance byte and rate limits could extend InstanceLimits (stored as instances.limits JSON, already read by llm-gw).
- Vault header injection fits the existing reveal path: check that vault_list is in the grant and the item allows this instance, write audit vault.use, and add the value to the scrubber. The proxy then needs the llmgw-style DB role, with SELECT on vault_items already granted, plus a per-destination binding for each item so a credential is never sent to a host the user did not pick.
- Package installs: there is no root and no compiler, so apt is out of scope. Global npm is root-owned. Workspace-local npm, pip in a venv, and git over HTTPS are what the proxy must serve. SSH git (port 22) would need a non-HTTP path, or should be refused.
- Cube needs a different identity story (node SNAT). Either rely on CubeEgress L7 header injection or keep Cube on a gateway-only allowlist until 2.7 covers it. The local backend has no isolation and can only be a dev passthrough.
- OpenClaw's ClawHub fetch after about 90 s must stay blocked under any allowlist (the clawhub.ai domains). Hermes auto-enables browser tools when Chromium is present (docs/browser.md:102-103), which affects which hosts it tries to reach.

## 摘要

Research on building a controlled internet channel (受管控的上网通道) for Thinktin's ACS sandboxes in Tokyo. The sources are primary vendor docs, standards pages and Chinese legal texts. The repo was only read, never changed.

BOTTOM LINE. There are three realistic ways to build it.

(A) SELF-BUILT EXPLICIT PROXY (recommended starting point). Run a forward proxy on the existing Tokyo service ECS (or a small ECS next to it). Sandboxes keep today's network-level deny-all. allowOut already allows the service machine IP; we add one security-group port. Each sandbox gets HTTP(S)_PROXY env vars. A tool that ignores the proxy therefore fails closed: its traffic is blocked, never leaked.
- The proxy can identify each sandbox by its Pod IP, because ACS pods are not SNAT'd. That is the same mechanism the model gateway already uses. An optional per-sandbox proxy token can be added.
- It enforces per-template and per-instance domain policy, does resolve-then-pin SSRF checks, and logs metadata only. It decrypts HTTPS (MITM) only for domains the user opted into for vault credential injection.
- Two ways to build it:
  1. Stripe Smokescreen (Go, MIT). It has run in Stripe production for years. Since v0.1.0 (2026-09-18) it supports CONNECT and plain HTTP, private-IP blocking that dials the exact IP it checked, per-role ACLs (mTLS CN or a custom RoleFromRequest), open/report/enforce modes, rate limits, and per-domain MITM with add_headers.
  2. A small Rust proxy. hyper's own http_proxy.rs example is about 150 lines. It would reuse the repo's existing llm-gw SSRF resolver, plus hudsucker (MIT/Apache) for opt-in MITM.
- Fixed cost is close to zero. Traffic is about 0.60 元/GB on Tokyo BGP public IP traffic.

(B) ALIBABA ACS "ENHANCED EGRESS TRAFFIC MANAGEMENT" (managed; launched May 2026). This is the managed version of what docs/vault.md plans.
- A traffic-proxy sidecar sits in each sandbox. Behind it, an Envoy-style egress-gateway and traffic-extension enforce SecurityProfile L7 rules. Rules can match domain (with wildcards), path, method, port, header and query.
- It can terminate TLS with an injected CA and inject credentials (ApiKey/STS, June 2026). It can also send audit webhooks.
- Default is ALLOW when no profile matches.
- It needs a NAT gateway for internet access.
- The default component sizing is 16 vCPU and 16 GiB. That is about ¥1,550 per month at ACS overseas rates (my calculation), before NAT. NAT adds about ¥130 per month fixed, 0.24 元/GB in CU fees and 0.60 元/GB in traffic.
- The component versions installable in our Tokyo cluster (sandbox-manager v0.6.13) appear to meet the requirements, but no one has tested this.

(C) NAT GATEWAY + CLOUD FIREWALL NAT-BOUNDARY ACLs. These ACLs filter by domain (Host/SNI) and source CIDR, and Tokyo is supported.
- Cost is 2.5 元/h per protected NAT gateway, about ¥1,825 per month, plus 0.36 元/GB. That comes on top of NAT.
- The default "loose" ACL mode lets unrecognised traffic through.
- Pod IPs change, so it is coarse for per-sandbox policy. It is best treated as a backstop, not the main policy engine.

HOW AI-AGENT PRODUCTS DO IT. All of them use deny-by-default with a domain allowlist. Most route traffic through a proxy outside the sandbox and offer preset lists.
- Anthropic srt / Claude Code cloud: HTTP and SOCKS proxies outside the sandbox. The proxy resolves a name once and dials the address it checked. Metadata addresses, including 100.100.100.200, are denied by default. Access levels are None, Trusted (about 215 default entries), Full and Custom. "Network secrets" are injected by the proxy, and a separate GitHub proxy holds the real token.
- OpenAI Codex: internet is off in the agent phase. Presets are None, "Common dependencies" (71 domains) and All. There is an optional GET/HEAD/OPTIONS-only mode.
- GitHub Copilot: a firewall with a recommended allowlist. It covers only Bash-tool processes, not MCP servers.
- E2B: allowOut/denyOut, with domain filtering only on 80 (Host) and 443 (SNI). 8.8.8.8 is auto-allowed. Header-injection transforms exist, but only on intercepted TLS.
- Daytona: tier-based limits.
- Modal: block_network, a CIDR allowlist and a domain allowlist.

SSRF ESSENTIALS.
- Resolve once, reject the request if ANY answer is non-public, and dial the validated IP while keeping the Host header and SNI.
- Normalise IPv4-mapped and NAT64 IPv6 addresses before checking.
- Block 100.64.0.0/10, which covers Alibaba metadata 100.100.100.200.
- Refuse IP-literal CONNECT unless explicitly allowed. Allow only ports 80/443 by default. Block SMTP.
- An SNI/Host mismatch (domain fronting) can only be checked after MITM.
- Remove sandbox DNS entirely. The proxy resolves names, which removes DNS tunnelling.

TOOL SUPPORT for the proxy env vars.
- Honour them: npm, pnpm, pip, uv, requests, httpx, cargo, git (HTTP only), curl (lowercase http_proxy only), Go net/http, apt, Deno, Bun fetch, and Chromium on Linux without GNOME/KDE.
- Node fetch and http need NODE_USE_ENV_PROXY=1 (http from v24.5, fetch from v24.0).
- Yarn Berry needs YARN_HTTP(S)_PROXY.
- Claude Code documents Bun as having proxy compatibility problems.
- Chromium does not send QUIC through a proxy. WebRTC UDP can leak unless disable_non_proxied_udp is set; network deny-all also stops it.
- Each runtime has its own trust store for an injected CA: NODE_EXTRA_CA_CERTS, REQUESTS_CA_BUNDLE, SSL_CERT_FILE, CURL_CA_BUNDLE, Chromium's NSS DB. Pinned clients break under MITM, so MITM should be opt-in per domain.

CHINA LAW.
- The Cybersecurity Law was amended on 2025-10-28 (in force 2026-01-01) and its articles were renumbered. Under the new numbering:
  - Log retention of at least 6 months is now Art. 23(3) (it was Art. 21).
  - Real-name for network access and information services is Art. 26 (it was Art. 24).
  - Stopping illegal information is Art. 49.
  These new numbers come from reposted full text. The official decision text only confirms the renumbering.
- The 公安部令第82号 requires at least 60 days of records, including login times, accounts and IP/domain.
- The MIIT 2017 notice (信管函〔2017〕32号) forbids unapproved self-built or leased lines, VPNs included, for cross-border business. The 1996 international-networking rules, Art. 6, require use of the state international gateways.
- Alibaba Cloud has sent customers notices for hosts that became "境内获取境外非法信息的途径", citing 互联网信息服务管理办法 Art. 15 and giving 24 hours to stop.
- 360's Tuber browser gave mainland users filtered access to YouTube and Google. It was pulled within days in October 2020.
- So a Tokyo egress that lets mainland users interactively browse blocked sites through our product is the main legal risk. Agent-only fetching of allowlisted resources is lower risk, but nothing official addresses it. A lawyer should review this before launch.

## 结论

- Recommended layering: keep network-level deny-all on every sandbox (allowOut = model gateway + proxy IP only, ports via security group), and add an explicit forward proxy that sandboxes reach through HTTP(S)_PROXY. Anything that ignores the proxy (UDP/QUIC, WebRTC, raw TCP, DoH, a tool with no proxy support) then fails closed instead of leaking. This is the same split Anthropic srt and Claude Code cloud use.
- Cheapest path: put the proxy on the existing Tokyo service ECS, which already has a pay-by-traffic public IP and is already allowed by allowOut. Open one proxy port to the sandbox vSwitch only. There is no new fixed cost; Tokyo BGP traffic is about 0.60 元/GB. Managed options add roughly ¥1,550/month (ACS enhanced egress components at default size, my calculation) or ¥1,825/month (one Cloud Firewall NAT instance), plus NAT (about ¥130/month fixed plus 0.24 元/GB CU).
- Per-sandbox identity is easy, because ACS pods are not SNAT'd. The proxy maps source Pod IP to sandbox to policy, the same way llm-gw already does. A per-sandbox proxy token in the proxy URL can be added as a second factor (curl, requests and Playwright support proxy credentials). The mapping must update when a sandbox is resumed and its Pod IP changes.
- Engine choice: Smokescreen (MIT, production-proven, already has resolve-then-pin, ACL modes, rate limits and per-domain MITM with add_headers) is the fastest way to a safe v1. A small Rust proxy (hyper CONNECT example + existing crates/llm-gw/src/ssrf.rs PublicOnlyResolver + hudsucker for opt-in MITM) fits the codebase and gives full control over per-sandbox policy, logging and vault integration. Either way, roles must come from Pod IP or token rather than Smokescreen's default mTLS CN, unless a custom RoleFromRequest is used.
- Policy model to copy from products: a per-template default list like Codex 'Common dependencies' (71 domains) or Claude 'Trusted' (about 215 entries) covering npm, PyPI, crates, apt, GitHub and Playwright browser hosts. On top of that, per-instance additions approved by the user on the phone, an optional 'read-only' mode allowing only GET/HEAD/OPTIONS (as in Codex), and an 'all domains' mode subject to the abuse controls below.
- Default deny rules regardless of allowlist: CONNECT only to ports 443 and 80, plus explicitly allowed others. No IP-literal CONNECT unless allowlisted. Block 25/465/587 (SMTP spam). Block all non-public ranges, including 100.64.0.0/10 (Alibaba metadata 100.100.100.200 and VPC internal service ranges), 169.254/16, RFC1918, ULA, link-local, IPv4-mapped and NAT64 forms. Resolve once, reject if any answer is non-public, and dial the checked IP. Do not follow redirects inside the proxy for HTTP.
- Give sandboxes no DNS: the proxy resolves names (clients send CONNECT host:port; SOCKS clients must use socks5h). This removes DNS-tunnel exfiltration, which E2B and the ACS enhanced mode leave partly open (8.8.8.8 auto-allowed; DoH/DoT not controlled). Today's allowOut already allows nothing else, but this should be verified on a live pod, including kube-dns.
- Env vars to set in the sandbox image or agent-shim: HTTP_PROXY, HTTPS_PROXY, http_proxy and https_proxy (curl reads only lowercase http_proxy), ALL_PROXY if SOCKS is offered, NO_PROXY=<llm-gw IP>, and NODE_USE_ENV_PROXY=1 (Node 24 base image; http needs >=24.5). Yarn Berry needs YARN_HTTPS_PROXY. Chromium should get an explicit --proxy-server (or Playwright proxy option) rather than relying on env, plus --force-webrtc-ip-handling-policy=disable_non_proxied_udp as defence in depth. Git over ssh and git:// will not work, so steer agents to https remotes (srt's deniedDomainReasons does this for github.com:22). Bun package fetching is a known trouble spot.
- TLS interception only for vault opt-in domains (credential header injection, as docs/vault.md plans). Install our CA into the sandbox only for that: SSL_CERT_FILE, NODE_EXTRA_CA_CERTS, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE, cargo http.cainfo and Chromium NSS DB. Keep all other traffic as opaque CONNECT tunnels. The proxy must fully validate upstream chains (CISA warning). Pinned or mTLS clients cannot be intercepted and must be excluded. Never inject a credential on an unintercepted or plain-HTTP request, and match the credential to exact hosts (E2B warns wildcards like *.com send credentials everywhere).
- Domain fronting and SNI/Host mismatch can only be enforced on intercepted domains. For opaque tunnels the proxy can at most check SNI against the CONNECT host, which needs a ClientHello peek; that is optional and adds work. A broad CDN or github.com allowance remains an exfiltration path, so an allowlist is not a full data-loss control.
- Abuse controls are needed before 'all domains' mode: per-sandbox and per-user connection, concurrency and byte caps (Smokescreen has max-request-rate and max-concurrent-connect-tunnels), a total bandwidth cap on the egress IP, an SMTP block, and alerting on scanning patterns (many distinct IPs or ports). Outbound attacks from our IP put the whole account at risk under Alibaba's security enforcement rules.
- Logging: one metadata line per connection (time, user, instance, sandbox, Pod IP, destination host:port, resolved IP, decision and reason, bytes up/down, duration). No URLs or bodies, except optional path/method for intercepted vault domains. Store it with the existing logs and keep it at least 6 months to meet the amended Cybersecurity Law Art. 23(3); 82号令 also requires at least 60 days. Opaque CONNECT naturally carries no content.
- Legal risk to raise with the founder: an agent browser in Tokyo that mainland users can watch or take over to read sites blocked in China (Google, YouTube and others) looks functionally like a cross-border access channel (MIIT 2017 notice, 国际联网暂行规定 Art. 6, Alibaba's '境内获取境外非法信息的途径' notices, Tuber precedent). Options to discuss: a category/domain blocklist for the user-facing live browser, real-name accounts (Art. 26), content handling per Art. 49 and GenAI Art. 14, and legal review before opening general browsing. Agent-only fetching of allowlisted developer resources is lower risk, but no official guidance was found.
- ACS enhanced egress management (B) is worth a short spike if we later want the managed version of vault credential injection or L7 path/method rules without running our own MITM. It defaults to allow, needs NAT, and costs about 16 vCPU at default sizing. It could also complement (A) as a cluster-level backstop, e.g. a GlobalTrafficPolicy denying 100.100.100.200/32 even if allowOut is later widened.
