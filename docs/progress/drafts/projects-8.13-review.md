### Share trigger silently leaves shared_at NULL when the inserting role cannot see the projects row

- 位置：`crates/store/migrations/0039_projects.sql:162`；评审定的：medium；核对：不成立
- 场景：project_members_share() is SECURITY INVOKER and runs `UPDATE public.projects SET shared_at = now() WHERE id = NEW.project_id AND shared_at IS NULL` with no check that a row was updated. Any inserter of a role='member' row that RLS stops from seeing projects gets 0 rows and no error. Reproduced on a scratch DB as the non-superuser owner, the way a future data migration would run (release.md only says to lift FORCE on the table you write): `BEGIN; ALTER TABLE project_members NO FORCE ROW LEVEL SECURITY; INSERT INTO project_members (project_id,user_id,role,consented_at) VALUES (<alice project>, <bob>, 'member', now());` gives INSERT 0 1, and projects.shared_at is still NULL. The same thing happens for any NOBYPASSRLS writer with no projects policy, such as the definer-function owners described in projects-impl item 2. With shared_at NULL, all of Alice's tenant policies still pass. `DELETE /v1/teams/{id}` then cascade-deletes Bob's member row, his agents and the invites. That breaks D3's claim that the 8.13 tenant policies are final. No such writer exists in 8.13 (only thinktin_worker, which bypasses RLS), so this is latent.
- 建议：Make the trigger fail loudly: `UPDATE public.projects SET shared_at = coalesce(shared_at, now()) WHERE id = NEW.project_id; IF NOT FOUND THEN RAISE EXCEPTION 'cannot mark project % shared', NEW.project_id USING ERRCODE = 'insufficient_privilege'; END IF;`
- 核对理由：I reproduced it on a scratch DB, migrated as thinktin_test_owner. The owner ran NO FORCE on project_members, inserted a role='member' row and committed. projects.shared_at stayed NULL. The same insert as thinktin_worker set it to true. So the mechanism is correct, but nothing in this build can reach it. A grep of crates/ shows no production path that inserts a role='member' row: projects.rs:65 only writes 'creator', the tenant_insert policy allows only role='creator', and erase_account only updates member rows. The only writer is thinktin_worker, which has BYPASSRLS. The definer functions in projects-impl item 2 are for read-only ProjectTx and thinktin_member, and the cross-user writes planned for 8.14 go through the worker. A future migration that inserts member rows while FORCE is still on projects is hypothetical. This is optional hardening, not a defect in 8.13.
- 核对建议：Optional hardening: in project_members_share(), use `UPDATE public.projects SET shared_at = coalesce(shared_at, now()) WHERE id = NEW.project_id; IF NOT FOUND THEN RAISE EXCEPTION ... USING ERRCODE = 'insufficient_privilege'; END IF;`.

### Tenant can re-activate a worker-marked dedicated agent row (forges an active dedicated agent)

- 位置：`crates/store/src/projects.rs:174`；评审定的：low；核对：不成立
- 场景：The 0039 comment (lines 196-197, 64) says the tenant cannot change dedicated. But replace_my_project_agents first marks removed agents left, keeping dedicated=true. When an agent is added back, the upsert's `DO UPDATE ... left_at = NULL` turns the old row back into an active dedicated row, and the tenant_update policy (0039:203-209) allows it. Reproduced as thinktin_app on Alice's solo project: the worker sets dedicated=true on a1. The tenant runs `UPDATE project_agents SET left_at = now()` (PATCH without a1), then the upsert from projects.rs:172-178 (PATCH with a1). Result: is_lead=t, dedicated=t, left_at=NULL. A plain tenant `UPDATE project_agents SET left_at = NULL` does the same. In 8.16 this gives an active dedicated row the worker never approved: fill_space's planned 'no private run on a dedicated instance' check would block the user's private runs. It can also turn a later team PATCH into a 409 on project_agent_dedicated when the instance is dedicated elsewhere.
- 建议：Add a BEFORE UPDATE trigger on project_agents: WHEN (OLD.left_at IS NOT NULL AND NEW.left_at IS NULL AND OLD.dedicated), and if current_user <> 'thinktin_worker', set NEW.dedicated := false. Trigger-assigned columns are not subject to the tenant's column grants. Alternatively, add `WHERE NOT (project_agents.dedicated AND project_agents.left_at IS NOT NULL)` to the upsert, return Conflict on 0 rows, and also reject the direct UPDATE in the policy or trigger.
- 核对理由：I reproduced the mechanism as thinktin_app. After the worker set dedicated=true on a1, the tenant marked it left and then ran the projects.rs:172-178 upsert. The row came back with is_lead=t, dedicated=t and left_at NULL. But nothing in 8.13 ever sets dedicated=true: the only write to dedicated is users.rs:216, which sets it to false, and the backfill leaves the default. So no reachable path produces this state. Even in 8.16, the restored flag is one the worker set on that same (project, instance) row. Per projects.md:69-70, dedicated is a cross-user feature, and once a project is shared the tenant_update policy blocks the tenant from touching its rows. If the instance has become dedicated elsewhere in the meantime, the project_agent_dedicated unique index rejects the reactivation with 23505, which maps to Conflict. That is a clean failure, not a forgery. The impact would fall only on the user's own instance. Whether rejoining should restore the flag is an 8.16 design question.
- 核对建议：None needed for 8.13. When 8.16 defines dedicated, decide whether re-adding an agent clears the flag. If it should, add a BEFORE UPDATE trigger that resets NEW.dedicated when OLD.left_at IS NOT NULL AND NEW.left_at IS NULL and current_user <> 'thinktin_worker'.

### writable_solo does not lock the project, so a concurrent share turns team PATCH into a 500 (RLS 42501) or 404 instead of 409

- 位置：`crates/store/src/projects.rs:203`；评审定的：low；核对：不成立
- 场景：writable_solo reads the project with a plain SELECT. Under READ COMMITTED each later statement takes a fresh snapshot, and the policy subqueries on projects take no lock. Reproduced: the tenant transaction runs the writable_solo SELECT (shared=f). The worker then inserts a role='member' row and commits, and the trigger sets shared_at. The tenant's next `UPDATE project_agents SET is_lead=false ...` silently affects 0 rows. The upsert then fails with 'new row violates row-level security policy for table project_agents' (42501), which becomes Error::Forbidden and HTTP 500 on PATCH /v1/teams/{id}. update_solo_project and delete_solo_project hit 0 rows in the same race and return 404 instead of 409. The transaction rolls back, so nothing partial is committed, but the status code is wrong and the policy race stays open once 8.14 joins exist.
- 建议：In writable_solo, after the classifying read, lock the row: `SELECT id FROM projects WHERE id = $1 FOR NO KEY UPDATE` (the tenant has UPDATE privilege, and the RLS UPDATE USING clause returns no row once the project is shared). Return Conflict when no row comes back. Verified on scratch that this makes the worker's share trigger wait until the tenant transaction commits.
- 核对理由：The analysis is correct. Under READ COMMITTED, the plain SELECT in writable_solo does not stop a later share. The later UPDATEs then affect 0 rows, and INSERT ... ON CONFLICT DO UPDATE fails the WITH CHECK or USING check with 42501. error.rs:51 maps that to Error::Forbidden, and gateway/src/error.rs:78 turns Forbidden into a 500. update_solo_project and delete_solo_project would return 404. But this build has no concurrent sharer: no code path inserts role='member', and only tests write it with raw worker SQL. The transaction rolls back completely, so the only effect is a wrong status code. The policies still enforce the rule. This is a latent 8.14 concern.
- 核对建议：For 8.14, when invite acceptance exists: in writable_solo, use `SELECT ... FROM projects WHERE id = $1 FOR NO KEY UPDATE` (the tenant has column UPDATE privilege; the UPDATE USING clause hides shared rows) and return Conflict when no row comes back. The worker's share-trigger UPDATE then waits for the tenant transaction.

### A concurrent instance delete and team PATCH can leave the deleted instance as the team's active lead

- 位置：`crates/store/src/projects.rs:224`；评审定的：low；核对：**成立**（low）
- 场景：I reproduced this on a scratch database at 0046, using the tenant role in two sessions. T1 runs `delete_instance(a2)`, where a2 is the team lead: it UPDATEs `instances` to `state='deleted'` and sets `left_at` on a2's `project_agents` row, but has not committed yet. T2 runs `PATCH /v1/teams/{id}` with members `[a2 lead, a1]`. In T2, `check_agents` calls `self.instance(a2)`, a plain SELECT that takes no lock, so it still sees a2 as alive. T2's first `UPDATE project_agents SET is_lead=false` then waits on a2's row. T1 commits. T2's clear-lead and mark-left statements now skip a2's row, and the `INSERT ... ON CONFLICT DO UPDATE` sets `left_at = NULL, is_lead = true` on it. Final state: a2 has `state='deleted'`, `left_at` is NULL and `is_lead` is true. `team()` hides a2, so the client sees a team with no lead, while `project_one_lead` and `is_team_lead(a2)` both treat a2 as the lead. This breaks the 8.13 rule that deleting an instance makes it leave every project. The next PATCH repairs it, but 8.14+ project views and dispatch will read the row in the meantime. No test covers the concurrent case.
- 建议：In `check_agents`, lock each instance row while checking it, for example with `SELECT 1 FROM instances WHERE id = $1 AND state <> 'deleted' FOR SHARE` (or make `instance_for_update` `pub(crate)` and call it). `delete_instance` already holds a row lock from its UPDATE, so the PATCH then waits for it, re-checks the row, sees `deleted`, and returns 404 instead of reviving the row.
- 核对理由：I reproduced this on a scratch database migrated to 0046. Tenant transactions use the default READ COMMITTED level (`Db::tenant` calls `pool.begin()` and sets no isolation). T1 ran the `delete_instance` statements for a2 (crates/store/src/instances.rs:385-402) and slept before committing. T2 ran `update_team`: `update_solo_project`, then `check_agents` (crates/store/src/projects.rs:224). That check calls `self.instance()`, a plain SELECT (instances.rs:291-301), so it still saw a2 as 'running'. T2's clear-lead UPDATE then blocked on a2's project_agents row. After T1 committed, the clear-lead and mark-left statements both reported UPDATE 0, and the upsert at projects.rs:171-177 took the DO UPDATE path. Final row: instance state 'deleted', project_agents is_lead=true, left_at NULL. The insert path has the same race and never blocks: the FK's KEY SHARE lock does not conflict with T1's NO KEY UPDATE on instances, so a deleted instance can also be added as a brand-new active member. The pre-8.13 `insert_members` had the same unlocked check, but before 8.13 deleted-instance rows in team_members were normal. The new invariant that deleting an instance makes it leave its projects (instances.rs:395) comes from 8.13, and this race breaks it. Impact in this build is small. `team()` and `delegation_targets` filter deleted instances. `is_team_lead` returns true only for an instance that can no longer run. The next PATCH with members clears the row, and `erase_account` resets it. So severity stays low: the invariant is violated, but there is no visible misbehaviour today. No test covers the concurrent case. I also checked the proposed fix on the same database: replacing the check with `SELECT ... WHERE id=$1 AND state<>'deleted' FOR SHARE` as thinktin_app is permitted, blocks behind T1, and then returns 0 rows. In the real code `fetch_one` turns that into NotFound and the transaction rolls back. If T2 takes the share lock first, T1's UPDATE waits and then marks the row left. Both lock orders end correctly, and no lock cycle is added (T2 locks projects then instances; T1 locks instances then project_agents).
- 核对建议：In `check_agents` (crates/store/src/projects.rs:224), stop using `self.instance(a.instance_id)` and lock each row instead: `sqlx::query_scalar::<_, Uuid>("SELECT id FROM instances WHERE id = $1 AND state <> 'deleted' FOR SHARE").bind(a.instance_id.0).fetch_one(self.conn()).await?;`. This blocks behind a concurrent delete and then returns NotFound (404). Optionally add a two-session store test that runs the delete and the PATCH at the same time.

### Re-adding a removed agent through the team API restores worker-owned `dedicated` (and `allow_computer`) without the worker

- 位置：`crates/store/src/projects.rs:174`；评审定的：low；核对：不成立
- 场景：Also reproduced as the tenant role. When an agent is removed in `replace_my_project_agents` (or by `delete_instance`), the code sets only `left_at`; `dedicated` and `allow_computer` keep their values, and the test `team_members_are_replaced_in_place` asserts that they do. When the same instance is added back, the upsert takes the `ON CONFLICT DO UPDATE` path and sets `left_at = NULL`. The tenant INSERT policy's `NOT dedicated` check runs only against the proposed new row, where `dedicated` defaults to false, so it passes. The worker-set `dedicated = true` therefore becomes active again with no worker involvement. Two outcomes follow. If the worker has since made that instance dedicated to another project, the PATCH fails with 409 `project_agent_dedicated`. Otherwise the instance is silently dedicated to the old project again. The tenant has no column grant on `dedicated`, so the API cannot undo either result.
- 建议：Have a BEFORE UPDATE trigger on `project_agents` reset `dedicated` and `allow_computer` to false when `OLD.left_at IS NOT NULL AND NEW.left_at IS NULL`. A trigger can write those columns even though the tenant has no grant on them. Alternatively, add `WHERE project_agents.left_at IS NULL OR NOT project_agents.dedicated` to the DO UPDATE and return a Conflict error when it affects 0 rows.
- 核对理由：The mechanism is accurate. I confirmed it on a scratch database: after a raw superuser `UPDATE project_agents SET dedicated = true`, a tenant removal followed by a re-add through the upsert at crates/store/src/projects.rs:171-177 leaves dedicated=true with left_at NULL. The INSERT WITH CHECK `NOT dedicated` only sees the proposed row, and the UPDATE policy does not look at dedicated. But nothing in this build can reach the scenario. No code path ever sets `dedicated` or `allow_computer` to true: the only writers are `users.rs:216`, which sets dedicated=false, and raw SQL in tests.rs. 0039 marks both columns as reserved for 8.16 and 8.18, and no migration from 0040 to 0046 or any claim query reads them. With both flags always false, the re-add restores nothing, so neither outcome can occur: the 409 from `project_agent_dedicated` and the silent re-dedication both need a worker that sets dedicated. Keeping the row in place is also a documented choice (replace_my_project_agents: per-agent settings are kept). Whether a re-joining agent should keep its dedicated or computer grant is an 8.16/8.18 product decision. Whichever way it goes, the dedicated/allow_computer API those packages add, which runs as the worker, can turn the flag off, so the 'tenant cannot undo' outcome is not permanent either. This is a design note for 8.16/8.18, not a defect in 8.13.
- 核对建议：No change needed in 8.13. When 8.16/8.18 adds the worker path that sets `dedicated` or `allow_computer`, decide what happens on re-join. If the flags should not survive a re-join, add a BEFORE UPDATE trigger on project_agents that resets both when `OLD.left_at IS NOT NULL AND NEW.left_at IS NULL`, and cover remove-then-re-add with a test.

### run_grants_project_agent is NO ACTION and grants are never deleted, so one project grant permanently blocks project deletion and account erase
