## authz-privacy

### Deleting a solo project cascade-deletes its invites, which resets the per-inviter daily cap and the per-phone notice cap

- 位置：`crates/store/src/project_invites.rs:309`；评审定的：high；核对：成立（high）
- 场景：Switch on, defaults invites_per_day=20 and invites_per_phone_per_day=5. Alice has a display name and one instance a1. She loops: POST /v1/projects {name, agents:[a1]} -> 201; then POST /v1/projects/{p}/invites {"phone": N} for up to 20 numbers -> 201 each, and every registered number gets a project_invite push; then DELETE /v1/projects/{p} -> 204. The delete succeeds because shared_at is still NULL while nobody has joined. It cascades projects -> project_members -> project_invites and removes every invite row. On the next project, both 24h counts start at 0 again. So one account can send unlimited invite pushes per day, and can push the same victim number again and again (invite, delete, invite...). Each deleted invite also leaves an unread project_invite inbox item, which raises the badge and opens to a 404.
- 证据：Both caps count live project_invites rows. Per inviter (project_invites.rs:311-315): `SELECT count(*) ... FROM project_invites WHERE inviter_id = $1 AND created_at > now() - interval '24 hours'`. Per phone (project_invites.rs:227-229): `SELECT count(*) FROM project_invites WHERE invitee_phone = $1 AND invitee_id IS NOT NULL AND created_at > now() - interval '24 hours'`. Those rows are deleted by cascade: 0039_projects.sql:33 has `project_members.project_id REFERENCES projects (id) ON DELETE CASCADE`, and 0039_projects.sql:88 has `FOREIGN KEY (project_id, inviter_id) REFERENCES project_members ... ON DELETE CASCADE`. The creator can delete any not-yet-shared project: projects.rs:523-533 `delete_solo_project` -> `writable_solo` (it only refuses when `p.shared`) -> `DELETE FROM projects WHERE id = $1`. The same path is reachable from DELETE /v1/teams/{id} (teams.rs:84-85). The FK cascade runs as the table owner, so the tenant's lack of rights on project_invites does not stop it. No test deletes a solo project that has invites.
- 建议：Keep the cap counts out of rows the inviter can delete. Simplest: refuse (409) to delete a solo project that has any invites created in the last 24h. The tenant cannot see invites, so do this check in a worker step or in a BEFORE DELETE trigger on projects. Alternatively, keep the per-inviter and per-phone counts in a small worker-only table that does not cascade. Either way, mark the invitees' project_invite inbox items read when their invites go away.
- 核对理由：Confirmed. Both caps count live project_invites rows. The per-inviter cap is invite_caps in project_invites.rs (~line 311: count(*) WHERE inviter_id=$1 AND created_at > now()-24h). The per-phone cap is the count WHERE invitee_phone=$1 AND invitee_id IS NOT NULL in the last 24h (~line 227). delete_solo_project (store/src/projects.rs:523) calls writable_solo, which refuses only when p.shared, and then runs DELETE FROM projects. While nobody has joined, shared_at stays NULL (it is set only by the project_members_share trigger on a role='member' insert), so pending, revoked or declined invites do not block the delete. The tenant_delete RLS policy allows the delete when shared_at IS NULL. 0039 cascades projects -> project_members (line 33) -> project_invites through FOREIGN KEY (project_id, inviter_id) ... ON DELETE CASCADE (line 88). In Postgres, RI cascade actions run as the referencing table's owner with SECURITY_NOFORCE_RLS, so the tenant having no grant or policy on project_invites does not stop the cascade. The function's own doc comment says invites are cascade-deleted. No FK references project_invites, and inbox_items.project_invite_id deliberately has no FK, so the delete succeeds and the inbox items are left behind. I found no limit on how many projects a user can create (no MAX_PROJECTS or rate limit), and POST /v1/projects only needs one of your own instances. The loop create -> invite xN -> delete therefore resets both 24h counts. One account can send unlimited project_invite pushes per day, to many numbers or repeatedly to one number. The pushes use dedupe_key and collapse_id of project_invite:{id}, and every new invite has a new id, so nothing collapses them. Revoking an invite does not reset the counts (the row stays), but deleting does. Blocking only helps a victim who has already identified the inviter, and the per-phone cap exists precisely to protect against floods. This is a cap bypass a real user can reach.
- 核对建议：Keep the cap evidence in rows the inviter cannot delete. For example, add a worker-only ledger, invite_sends(inviter_id, invitee_phone_or_null, delivered bool, created_at) with no FK cascade from projects, inserted in create_phone_invite/create_link_invite, and count both caps from it. Or refuse (409) DELETE of a solo project that has invites created in the last 24h, checked in a worker step or a BEFORE DELETE trigger, because the tenant cannot see project_invites. Also mark the invitees' project_invite inbox items read when their invites are removed with the project.

### A member calling DELETE /v1/projects/{id} gets 404 instead of 403

- 位置：`crates/gateway/src/routes/projects.rs:148`；评审定的：low；核对：成立（low）
- 场景：bob is a live member of alice's shared project p. GET /v1/projects/{p} returns 200 for him, but DELETE /v1/projects/{p} returns 404 "not found". The plan's status table says a member calling a creator-only route gets 403 `forbidden`. A client that follows the documented contract will treat the project as gone. The outsider test covers only the other creator-only routes for 403, not this one.
- 证据：`delete` opens a tenant transaction and calls `t.delete_solo_project(id)` -> `writable_solo` -> `own_project(id)`. That read goes through the tenant RLS policy `tenant_read ON projects USING (creator_id = app_user_id())` (0039:181), so for a non-creator member it gets RowNotFound -> store::Error::NotFound -> 404. It never checks membership the way the worker `project_actor`/`require_creator` routes do.
- 建议：When the tenant delete returns NotFound, check membership with a worker read (for example `projects::detail`, or a role lookup) and return `ApiError::new(ErrorCode::Forbidden, ...)` for live members. Keep 404 for outsiders.
- 核对理由：Confirmed. routes/projects.rs delete opens a tenant transaction and calls delete_solo_project -> writable_solo -> own_project. own_project reads projects under the tenant_read policy USING (creator_id = app_user_id()) (0039:181), so for a member it gets RowNotFound -> NotFound -> 404. There is no membership check. That contradicts the plan's status table ('403 forbidden: a member calling a creator-only route'; DELETE /v1/projects/{id} is listed as creator-only) and docs/projects-impl.md ('成员调只有创建者能用的接口 403'). The outsider test checks 403 for members only on GET invites, PATCH, POST invites and DELETE agents, not on DELETE /v1/projects/{id}, so nothing catches this. The impact is a contract mismatch (the client may treat the project as gone); no data is exposed, because the member can already see the project.
- 核对建议：In routes/projects.rs delete, when delete_solo_project returns store::Error::NotFound, run a worker membership check (for example a role lookup like the one project_invites uses, or projects::detail succeeding). Return ApiError forbidden for a live non-creator member and keep 404 for outsiders. Add DELETE /v1/projects/{p} to the member 403 loop in outsiders_see_nothing_of_a_project.

### A member can flood the creator with lock-screen pushes carrying member-controlled text by adding and withdrawing an agent in a loop

- 位置：`crates/orchestrator/src/projects.rs:337`；评审定的：low；核对：成立（low）
- 场景：bob is a member of alice's project. He renames his instance b1 to any text (an ad or abuse), then loops POST /v1/projects/{p}/agents {agents:[b1],consent:true} and DELETE /v1/projects/{p}/agents/{b1}. Each DELETE sends alice an Info push like "Bob withdrew the agent “<text>” from “P”". Nothing dedupes or collapses these pushes; only the generic per-user limiter of 1200/min bounds them.
- 证据：In `withdraw_agent`, the branch `else if out.owner != out.creator { ... texts::project_agent_left(locale, out.owner_name, &out.name, &out.project_name); let notice = project_notice(...PROJECT_AGENT_LEFT); notify(&mut w, out.creator, &notice) }` sets no `dedupe_key` or `collapse_id`. `out.name` is the owner-editable `instances.name` (project_members.rs:227-229). `add_project_agents` re-activates the left row in place, so the add/withdraw cycle can repeat without limit.
- 建议：Give project_agent_left (and project_agent_removed) a `collapse_id` of `project_agent:{project}:{instance}` and a time-bucketed `dedupe_key`, or write these receipts only to the inbox without a push.
- 核对理由：Confirmed. Each time withdraw_agent runs with user == owner != creator, it calls notify(creator) for a PROJECT_AGENT_LEFT notice. That notice has no dedupe_key or collapse_id (project_notice sets neither), so insert_inbox writes a new row and a new push every time. The text from texts::project_agent_left includes the owner's display name and i.name, both set by the member. add_project_agents treats a left row as not live (live_agents), so put_agents re-activates it. A member can therefore cycle POST /agents {consent:true} and DELETE /agents/{b1} indefinitely, bounded only by the generic per-device and per-user request limiters (600 and 1200 per minute). The plan's receipt table does not specify any dedupe for this receipt, so this is an omission rather than a decision. The severity is low: the attacker must already be a member the creator invited, and the creator can stop it by removing them. The creator can do the reverse with project_agent_removed only if the member keeps re-adding.
- 核对建议：Give project_agent_left and project_agent_removed a collapse_id of project_agent:{project}:{instance}, plus a dedupe_key bucketed by time, for example project_agent_left:{project}:{instance}:{hour}, so repeated cycles collapse on the device and write at most one inbox row per window. Alternatively, write these receipts to the inbox only, without a push.

## concurrency

### Deleting an unshared project resets the per-inviter and per-phone daily caps, allowing unlimited invite pushes

- 位置：`crates/store/src/project_invites.rs:311`；评审定的：high；核对：成立（high）
- 场景：Mallory sets a display name, then loops: POST /v1/projects (one of her instances), POST /v1/projects/{id}/invites {"phone": victim}, DELETE /v1/projects/{id}. No one ever joins, so shared_at stays NULL and the tenant delete is allowed. The delete cascades the project's project_invites rows away (project_members ON DELETE CASCADE, then project_invites (project_id, inviter_id) ON DELETE CASCADE). On the next round, invites_per_day (20) counts 0 and the victim's delivered-notice count (5 per day) is 0 again, so every round sets invitee_id and notify() sends another inbox item and push. The victim gets unlimited "Someone invited you to a project" pushes. They cannot block the sender: the invite and project are gone, so GET /v1/project-invites/{id} returns 404 and no inviter id is ever shown.
- 证据：Per-inviter cap: `SELECT count(*), … FROM project_invites WHERE inviter_id = $1 AND created_at > now() - interval '24 hours'` (project_invites.rs:311-315). Per-phone cap: `SELECT count(*) FROM project_invites WHERE invitee_phone = $1 AND invitee_id IS NOT NULL AND created_at > now() - interval '24 hours'` (:227-233). Both count rows that `Tx<Tenant>::delete_solo_project` (projects.rs:523-533, reached from DELETE /v1/projects/{id} and DELETE /v1/teams/{id}) deletes by cascade. writable_solo only refuses when `p.shared`, and pending invites never set shared_at. The inbox and outbox rows survive the delete (no FK on project_invite_id; outbox has no FK).
- 建议：Count from rows that survive a project delete. One option: insert a ledger row per created invite (inviter_id, invitee_phone, delivered, created_at) in a table with no cascade, and purge it after 24h. Another: have delete_solo_project return 409 while the project has invites created in the last 24h, or treat any project that has sent an invite as shared.
- 核对理由：Confirmed by reading the code. 0039 defines project_members.project_id REFERENCES projects ON DELETE CASCADE and project_invites (project_id, inviter_id) REFERENCES project_members ON DELETE CASCADE. RI cascades run as the table owner and ignore FORCE RLS, so a tenant DELETE FROM projects removes the project's invite rows. Tenant delete_solo_project (projects.rs:523-533, reached from DELETE /v1/projects/{id} and DELETE /v1/teams/{id} via teams.rs:85) goes through writable_solo, which refuses only when shared_at is set. A pending invite never sets shared_at; only the project_members_share trigger on a member INSERT does. Both caps count rows from project_invites alone. The per-inviter cap is invite_caps :311-319 (inviter_id + created_at); the per-phone cap is :227-233 (invitee_phone + invitee_id IS NOT NULL + created_at). After a delete, both counts drop back. Nothing else limits this. The gateway keeps no in-memory invite bucket (plan 4.2 dropped it), so only the 1200/min per-user limiter applies. Each new invite has a new id, so notice.dedupe_key and collapse_id (orchestrator projects.rs:104-105) differ and every round pushes again. The push text is generic. The inbox item has no FK, and GET /v1/project-invites/{id} 404s once the rows are gone, so the victim never sees the inviter's id and cannot block. Revoking would not reset the counts, because revoked rows stay; only a delete does. Reachable by any user with a display name and one instance once cross_user_projects is on. This is a cap bypass that enables push harassment: high.
- 核对建议：Count from data that a project delete does not remove. For the per-phone cap, either count the recipient's inbox_items with subtype 'project_invite' in the last 24h (those rows have no FK and survive), or add a small non-cascading ledger table (inviter_id, invitee_phone or its hash, delivered, created_at) that is purged after 24h. For the per-inviter cap, count that ledger or the 'project.invite.create' audit rows by the inviter. Another option: make delete_solo_project return 409 while the project has invites created in the last 24h, or treat a project that has sent invites as shared for tenant deletes.

### add_project_agents (agent row, then instance) deadlocks with the tenant instance delete (instance, then agent row) on solo projects

- 位置：`crates/store/src/project_members.rs:177`；评审定的：medium；核对：成立（medium）
- 场景：Alice has solo project S with live agent I. At the same moment she sends POST /v1/projects/S/agents with [I, K] (for example a client that resends the full list) and DELETE /v1/instances/I. Tx A (worker) locks row (S,I) FOR NO KEY UPDATE, then waits for FOR SHARE on instance I. Tx B (tenant) already holds I, from cancel_instance_runs' epoch bump or delete_instance's `UPDATE instances SET state='deleted'`. It then runs `UPDATE project_agents … WHERE instance_id = I AND left_at IS NULL`; RLS lets this touch (S,I) because S is unshared, and it waits on A. Postgres detects the cycle after deadlock_timeout and aborts one request with 40P01, which surfaces as a 500.
- 证据：project_members.rs:177-186 runs `SELECT 1 FROM project_agents WHERE project_id = $1 AND instance_id = ANY($2) ORDER BY instance_id FOR NO KEY UPDATE` and then `lock_own_instances` (`… FROM instances … FOR SHARE`). instances.rs:385-402 (tenant delete_instance, no project lock) runs `UPDATE instances …` and then `UPDATE project_agents SET is_lead = false, left_at = now() WHERE instance_id = $1 AND left_at IS NULL`. Those are opposite orders on the same two rows, and both write paths reach unshared projects.
- 建议：In add_project_agents, call lock_own_instances before touching project_agents rows, as accept_invite already does. The explicit project_agents row lock is redundant under the project lock and can be dropped. Alternatively, have the tenant delete take the project locks of the instance's solo projects before updating the instance.
- 核对理由：Confirmed. In add_project_agents (project_members.rs:177-186), the worker locks the existing project_agents rows FOR NO KEY UPDATE and then takes the instance rows FOR SHARE in lock_own_instances (:99-114). The gateway instance delete (routes/instances.rs:378-383) is one tenant transaction that takes no project lock. It updates the instance row: bump_epochs in cancel_instance_runs, and then delete_instance's UPDATE instances at instances.rs:385. That is a non-key update, so a FOR NO KEY UPDATE tuple lock, which conflicts with FOR SHARE. Only then does it run UPDATE project_agents ... WHERE instance_id = $1 AND left_at IS NULL (:396-402). Tenant RLS lets that UPDATE match the row in the user's unshared project, and it needs a lock that conflicts with the worker's FOR NO KEY UPDATE. Before these two rows, neither transaction takes a lock that would serialize them: the worker's users FOR KEY SHARE, advisory project lock and member-row lock are never requested by the tenant delete, and the audit FK takes only KEY SHARE. So with I live in solo project S, POST /v1/projects/S/agents including I, run at the same time as DELETE /v1/instances/I, forms a cycle. Postgres aborts one with 40P01, which surfaces as a 500. The tenant delete breaks D3: it takes instances (step 9) before project_agents (step 7) and skips the D4 project lock. It is a narrow race between one user's own requests and resolves to a single failed, retryable request, so medium rather than high.
- 核对建议：Either drop the explicit project_agents row lock in add_project_agents (the project advisory lock already serializes worker writers), so the worker blocks only on the instance FOR SHARE and then sees the instance deleted and returns NotFound. Or, closer to D3/D4, have the tenant instance delete take lock_project for each unshared project that holds the instance (in id order) before its first instance or run update.

### A removed member can rejoin through a pending phone invite created while they were a member

- 位置：`crates/store/src/project_members.rs:403`；评审定的：medium；核对：成立（medium）
- 场景：Alice invites Bob's number to P. The response is a uniform 201 and Alice cannot tell he is already a member, because Bob joined earlier via a link or with a different invite. The store still inserts a pending phone invite, valid for 7 days. Bob cannot see it while he is a live member. Alice then removes Bob. Now Bob is not a live member, so GET /v1/project-invites lists the old invite, and POST /v1/project-invites/{id}/accept passes every check: phone match, not suppressed, not blocked, not a live member. Bob is back in the project without a fresh invite and the removal is undone.
- 证据：create_phone_invite inserts the pending row even when `member` is true and only withholds the notice: `deliver_to = recipient.filter(|_| !blocked && !member && !over)`, then INSERT (project_invites.rs:234-262). for_me_sql hides the invite only while `m.left_at IS NULL` (project_invites.rs:153-154). exit_member's only invite cleanup is `UPDATE project_invites SET status = 'revoked' … WHERE project_id = $1 AND inviter_id = $2` (project_members.rs:403-410), which covers invites the member sent, not invites addressed to the member's phone.
- 建议：In exit_member when reason is 'removed', also run `UPDATE project_invites SET status='revoked', settled_at=now() WHERE project_id=$1 AND kind='phone' AND status='pending' AND invitee_phone=(SELECT phone FROM users WHERE id=$2)`. The project lock and the member's users row are already held. Then mark the matching inbox items read.
- 核对理由：Confirmed. create_phone_invite inserts the pending row even when the recipient is a live member and only withholds deliver_to (project_invites.rs:234-262). accept_invite settles only the invite that was used, so a phone invite to Bob stays pending after Bob joins by a link. This is the natural case: the creator sends a phone invite and a link, and Bob uses the link. for_me_sql hides the invite only while m.left_at IS NULL (:153-154). exit_member's only invite cleanup is the inviter_id revoke at project_members.rs:403-410, which covers invites the member sent. After remove_project_member, the old phone invite reappears in GET /v1/project-invites. accept_invite then passes every check: phone matches, not suppressed, not blocked, live_member false. The ON CONFLICT ... DO UPDATE WHERE role='member' AND left_at IS NOT NULL path reactivates the member row. So the removed member rejoins with no new action by the creator. Mitigations: the creator gets a joined notice and can remove again (the stale invite is consumed by then), and the invite shows as pending (masked) in her list. The removal is still undone by an invite she cannot tell targets that person, so it is wrong behaviour a user can hit.
- 核对建议：When a member is removed (and preferably also on leave), revoke pending phone invites in that project addressed to the member's phone: UPDATE project_invites SET status='revoked', settled_at=now() WHERE project_id=$1 AND kind='phone' AND status='pending' AND invitee_phone=$phone RETURNING id, using the phone from the already-locked users row, then read_invite_items for the member. Put it before the member and agent row updates to keep D3's order: invite rows before other members' rows. Also consider settling the member's other pending phone invite to the same project when they join through a different invite.

### purge_project_invites takes invite rows without SKIP LOCKED, so this sweep waits and can deadlock

- 位置：`crates/store/src/project_invites.rs:886`；评审定的：low；核对：成立（low）
- 场景：maintain's purge deletes up to 500 settled invite rows in settled_at/plan order. At the same time an erase_account (`DELETE FROM project_invites WHERE inviter_id = $1 OR invitee_id = $1 OR accepted_by = $1 OR invitee_phone = …`, BitmapOr scan order) or a tenant delete_solo_project (cascade order) deletes an overlapping set of 30-day-old rows in a different order. Each statement holds one row the other needs, and Postgres aborts one with 40P01: either the user's account deletion fails, or maintain returns Err.
- 证据：`DELETE FROM project_invites WHERE id IN (SELECT id FROM project_invites WHERE status <> 'pending' AND settled_at < now() - make_interval(secs => $1) LIMIT $2)` has no `FOR UPDATE SKIP LOCKED`, unlike expire_project_invites (:859-860). D3 says "Sweeps never wait. Invite and inbox rows are taken FOR UPDATE SKIP LOCKED".
- 建议：Add `FOR UPDATE SKIP LOCKED` (with ORDER BY settled_at) to the purge subquery.
- 核对理由：Confirmed. purge_project_invites (project_invites.rs:885-893) deletes up to `batch` settled rows with no FOR UPDATE SKIP LOCKED. The expire sweep at :859-860 has it, and D3 states that sweeps never wait and take invite rows FOR UPDATE SKIP LOCKED. Overlapping deletes in a different order are reachable: erase_account's DELETE ... WHERE inviter_id OR invitee_id OR accepted_by OR invitee_phone (users.rs:235-236), and a tenant delete_solo_project cascade, which runs per inviter member row and likely in project_invites_project (created_at DESC) order versus the purge's settled_at order. Either can delete the same 30-day-old settled rows at the same moment as the purge, and opposite lock orders on two rows give 40P01. The sweep can also block behind accept or revoke, which lock invite rows FOR UPDATE whatever their status. The window is small and the result is a retryable error (one erase 500s, or maintain returns Err), so low.
- 核对建议：Use `DELETE FROM project_invites WHERE id IN (SELECT id FROM project_invites WHERE status <> 'pending' AND settled_at < now() - make_interval(secs => $1) ORDER BY settled_at LIMIT $2 FOR UPDATE SKIP LOCKED)`.

### decline and create_phone_invite check expiry with now() (transaction start) after waiting on locks

- 位置：`crates/store/src/project_invites.rs:731`；评审定的：low；核对：不成立（low）
- 场景：(a) Bob declines invite X a moment before expires_at. His transaction waits on the project lock, for example behind Alice's revoke or invite on P, until after expiry. The locked re-check `i.expires_at > now()` uses the transaction start time, so X is settled 'declined' instead of 'expired', which also reveals to the inviter that the number is registered. (b) Alice re-invites a number whose pending invite expires while her transaction waits on the project lock. The in-place expiry `expires_at <= now()` misses it, the `existing` check has no expiry filter, and she gets back the dead invite with created=false: no new invite, no notice, and status shown as 'pending'.
- 证据：decline_invite's locked re-check: `… AND i.expires_at > now() AND i.suppressed_at IS NULL …` (project_invites.rs:728-733). create_phone_invite: `UPDATE … SET status = 'expired' … AND expires_at <= now()`, then `SELECT id … AND status = 'pending'` (:199-216). accept_invite uses statement_timestamp() for exactly this reason (plan C3), but these two paths do not.

### A member calling DELETE /v1/projects/{id} gets 404, not the 403 the plan specifies for creator-only routes

- 位置：`crates/gateway/src/routes/projects.rs:143`；评审定的：low；核对：成立（low）
- 场景：Bob, a live member of Alice's shared project, sends `DELETE /v1/projects/{p}`. He gets 404 `not_found`, because the handler runs a tenant `delete_solo_project` and creator-only RLS hides the row. Every other creator-only route (PATCH, invites list/create/revoke, member remove) gives a member 403 `forbidden`, as the plan's status table says. A client following the plan will read the 404 as "project gone" and may drop it from the UI, even though Bob can still `GET` it.
- 证据：`pub async fn delete(...) { let mut t = s.db.tenant(who.user).await?; t.delete_solo_project(id).await?; ... }`. `writable_solo` calls `own_project` under tenant RLS and returns `Error::NotFound` for a project the caller didn't create. The plan's 403 row: "a member calling a creator-only route".
- 建议：Before the tenant delete, check membership with a worker read (for example `projects::detail`, or a small `project_role` read). Return `ApiError::new(ErrorCode::Forbidden, …)` for a live non-creator member and 404 for outsiders. Add the case to `outsiders_see_nothing_of_a_project`.
- 核对理由：Confirmed. `routes/projects.rs::delete` runs tenant `delete_solo_project`, and that calls `writable_solo`, then `own_project`. The tenant RLS policy `tenant_read ON projects ... USING (creator_id = app_user_id())` (0039_projects.sql:181) hides the row from a member, so `fetch_one` gives RowNotFound, then `Error::NotFound`, then 404. The plan's route table lists DELETE as "creator", and the status table puts "a member calling a creator-only route" under 403 (a member's project is shared, so 409 would also fit the table). Today a live member, who can still GET the project, is told it does not exist. PATCH, the invite routes and member removal return 403 through the worker `require_creator` path. `outsiders_see_nothing_of_a_project` does not cover DELETE /v1/projects/{p} for either carol or bob. Low.
- 核对建议：In `projects::delete`, first do a worker read of the caller's role (for example via `projects::detail`, or a small role lookup). Return `ApiError::forbidden` for a live non-creator member, keep 404 for non-members, then run the tenant delete for the creator, which gives 409 when shared. Add DELETE /v1/projects/{p} to both loops in `outsiders_see_nothing_of_a_project`.
