# 联网搜索评审原始结果（2026-11-04，4 个方面，每个方面一个反驳者）

## tool

### [成立] [medium] web_search runs inline on the run's event loop: slow backends block lease renewal, stop and other events, and parallel searches can lose the lease

Confirmed by reading the code. In executor.rs (around lines 1837-1858), `ShimEvent::PlatformToolCall` awaits `self.call_tool(...)` inside `on_event`, which runs inside the `ev = self.session.events.recv()` arm of the biased select (line 1716). Only computer tools are spawned into `computer_calls`. `SearchTools::search` tries each backend in turn with a 15 s reqwest timeout (`search_client(timeout_secs=15)`), so one call can take about 30 s when both backends hang. The bridge client (`run_client`) does not wait for one reply before reading the next request, and `serve_conn` spawns each call, so concurrent tools/call requests become back-to-back PlatformToolCall events. I checked the local Claude Code binary (2.1.318): its MCP tool has `isConcurrencySafe(){return Me.mayOverlap||(oe.annotations?.readOnlyHint??!1)}`, so the new readOnlyHint makes Claude run several web_search calls at once. With `biased`, a queued event beats `renew.tick`, so renewal starves for the whole burst. The lease is 60 s and renewal runs every 15 s (workers.rs: lease_secs/4). takeover_every is 15 s and does not exclude the executor's own node. `take_over_expired` then finishes the run with Retry, which goes to Backoff with release_lease, so the next renew fails and the turn is lost. Cancellation and shutdown are also only seen between calls. The lease loss only happens when a backend is slow or hanging (for example DeepSeek timing out and 3-4 parallel searches). That is realistic but not the normal path, so medium.

修法：Run non-side-effect slow platform tools such as web_search off the select loop. Spawn them into a JoinSet like `computer_calls` (call_id, ToolOutput) and send PlatformToolResult when each finishes. Also give the backend fallback chain one overall deadline (for example 10-15 s total, with a short connect_timeout per backend) instead of a full timeout_secs per backend.

### [成立] [medium] "Stop and alert" on the ¥100 monthly cap only stops: nothing actually alerts the operator

Confirmed. The founder's decision is "到了就停下、提醒用户", and the plan text in search.md (line 167: "每月总额快用完时提醒你", line 217: "每月总额提醒") promises a reminder. The implementation only calls `error!(...)` and bumps the counter/gauge in `SearchReserve::MonthlyBudget`. There is also no warning as the cap gets close. No code path notifies anyone. config.rs has no operator webhook or admin channel. deploy/ ships only `prometheus.io/scrape` annotations: no Prometheus, alert rules or Alertmanager. The Tokyo plan says 不开 SLS (deploy-aliyun-sg.md:192), so the error line exists only in pod stdout. DeepSeek is prepaid, so a 402 once the small top-up runs out is a very plausible way for this to start. That 402 silently falls back to IQS at 1.6x the price, which moves spend toward the cap, and then every agent's search stops with nobody told. If only DeepSeek is configured, every call fails with per-call `warn!` only, and the agent is told "try again later". The cost guard itself works, so this is a missing notification rather than overspend.

修法：On the first MonthlyBudget refusal in a month, and optionally when spend crosses about 80%, send a one-shot operator notification through an existing channel (inbox or push to a configured admin user, or an IM webhook setting). Deduplicate it per month with a DB row. Treat a repeated 401/402 from a backend the same way. Return a non-retry message for 401/402 instead of "try again later".

### [驳回] [low] Migration 0036 skips revoked and agent-created plan grants; plans resumed after 全部停止 or confirmed later never get web_search

The code path exists: `ensure_plan_grant` copies `g.scope` from the revoked or child grant, and 0036 filters `parent_id IS NULL AND revoked_at IS NULL`. But nobody realistically hits it. Only grants that already exist when the migration runs are affected, and no environment has been deployed (search.md "东京还没部署"; progress docs say the server machine has not been bought). There is no user data with stop_all'd or pending-confirmation plans to miss. Every grant created after the migration gets `default_scope`, which now includes web_search through `Api::default_platform_tools`, so later stop_all/resume or confirm keeps web_search. The filter is also the same one used by 0024/0026 for earlier tool additions. Pending child grants also expire under grant_ttl.

修法：No change needed for this release. If it matters later, have `ensure_plan_grant` merge the current default platform tools into the copied scope instead of relying on per-migration backfills.

### [成立] [low] A partial [search.<vendor>] override silently sets the price to 0, so that backend's spend never counts toward the monthly cap

Reproduced with a scratch crate that mirrors the structs (serde container `#[serde(default)]` on a `Default`-derived `SearchVendor`). `[search.iqs] endpoint="https://cloud-iqs..." engine="GlobalAdvanced"` deserializes to `price_per_1000_fen: 0`. An override with only engine or only price leaves endpoint empty, and `validate` rejects that (https check), which pushes the operator to add the endpoint while price stays 0. `validate` never checks the price or the IQS engine. With price 0, `cost_millicents()` is 0. Actual spend for that backend is then never recorded, and if it is the only backend the reservation is 0 too, so the ¥100 cap never fires. GlobalAdvanced costs ¥56 per 1000, which makes the undercount costly. This only happens on an operator config edit, so low.

修法：Give `SearchVendor` per-vendor defaults, for example separate DeepSeek and IQS structs, each with its own `Default` and `#[serde(default)]`. Also have `validate` reject `price_per_1000_fen == 0`, and an empty `engine` for iqs, for every provider listed in `providers`.

### [成立] [low] per_user_daily = 0 still allows one search per user per day

Confirmed with psql against DATABASE_URL using the same `INSERT ... ON CONFLICT DO UPDATE ... WHERE calls < $4 RETURNING calls` shape. With limit 0, the first insert returns calls=1 (Reserved) and only the second returns no row (UserDaily). Neither `SearchTools::search` nor `Config::validate` special-cases 0. An operator who sets `[search] per_user_daily = 0` to pause search still gets one paid search per user per day. Setting providers = [] stops search completely, so the impact is small.

修法：Return `SearchReserve::UserDaily` up front in `reserve_search` (or in `SearchTools::search`) when `per_user_daily == 0`, or make the insert conditional (`INSERT ... SELECT ... WHERE $4 > 0`).

## agents

### [成立] [medium] OpenClaw's built-in web_search is still on, has no provider, and fails on every call next to the new thinktin__web_search

Confirmed in the OpenClaw 2026.10.3 dist. createWebSearchTool (openclaw-tools-BA3mvtXt.mjs:17284-17286) returns null only when `enabled === false` or `tools.web.search.enabled === false`. It is added to the tool list unconditionally (17426-17431), and web_search is in the coding profile and in the default no-profile set (tool-catalog:258-262). Nothing hides it when no provider exists: hasUsableWebSearchProvider is only used for cron diagnostics (run-fallback-policy:170). The only filter, applyModelProviderToolPolicy, removes it only when the route is `native`. That route needs provider openai/Codex, and ours is `thinktin` behind the gateway URL. The openclaw.json rendered in config.rs openclaw() has only `tools.exec`, and inject_mcp adds only `mcp.servers`. No provider key exists either (provider is thinktin; no BRAVE/KIMI/OPENROUTER/... env), and key-free providers never win auto-detection (docs/tools/web.md:270-277). So every call reaches runWebSearch, which throws 'web_search is disabled or no provider is available.' (runtime-DBx9mneI.mjs:242). It gets worse: with `tools.toolSearch` unset, embedded runs use Tool Search by default, and MCP tool names and descriptions are not copied into the system prompt (docs/tools/tool-search.md). The model therefore sees the trusted core `web_search` but has to discover `thinktin__web_search` by searching, so the failing tool is the one it reaches for first. Founder decision 3 keeps vendor-side search (Claude WebSearch, Codex). This tool is not vendor search and has nothing behind it, and docs/search.md step 2 planned to disable exactly it.

修法：In openclaw() (or in the OpenClaw branch of inject_mcp), set `config["tools"]["web"] = json!({"search": {"enabled": false}})`, merged next to `tools.exec` and leaving `tools.web.fetch` alone. Assert `v["tools"]["web"]["search"]["enabled"] == false` in platform_tools_go_into_pi_and_openclaw_configs. Optionally also set `tools.toolSearch: false`, or give the server a `description`, so thinktin__web_search is directly visible.

### [成立] [low] OpenClaw gets every platform tool (computer_*, delegate, ask, schedule_*, vault_*) with no per-call approval, although Pi was cut down to web_search for that same reason

The facts check out. inject_mcp adds `--only` only for Pi, and the OpenClaw branch injects the bridge unfiltered. OpenClaw's ACP bridge relays only exec approval events to ACP requestPermission: server-CIY0aWW3.mjs handleApprovalEvent → parseGatewayExecApprovalEventData, and findPendingForApproval matches only tool calls of kind `execute`. MCP tools have no before-call approval in the native runtime; docs/tools/mcp.md 'Approvals' covers only Codex-harness MCP. So computer_write_file/type/click/open/key, delegate, ask and schedule_* run with no app-side prompt, while Claude and Codex ask by default (PlanPolicy.preauthorized_tools is empty). This contradicts the change's own Pi rationale ('no permission system, so only search'), and docs/search.md marks OpenClaw MCP approval as unverified. The impact is bounded, so I rate it low rather than medium. Platform tools are built on the assumption that agents are untrusted: agent-created plans start paused until the user confirms, vault_* never reveals values, computer_delete/run need a phone signature every time, and Normal-risk computer ops need a capability token the user issued from the phone. Hermes already has the same exposure (agent-integration.md:105-108), and the doc says the security boundary is the microVM. What remains is prompt-injected computer_type/click/write_file into apps and folders the user pre-allowed, which Claude and Codex would have prompted for.

修法：Treat OpenClaw like Pi until there is an approval path: add the same `--only` list (rename PI_PLATFORM_TOOLS to a shared NO_APPROVAL_PLATFORM_TOOLS) to the OpenClaw entry, or set `mcp.servers.thinktin.toolFilter.include = ["web_search"]`, and at minimum exclude computer_*. Otherwise record the decision explicitly in docs/search.md and docs/agent-integration.md (OpenClaw = Hermes: all platform tools, no approval). Enforce it shim-side as well (see the next finding).

### [成立] [low] `--only` is enforced only in the in-sandbox mcp-bridge client; the shim socket still serves every granted tool to Pi

Confirmed. executor.rs:837-843 sends Pi's shim every granted platform tool (filtered only by grant and lead status, never by agent). serve() in main.rs passes the full list to Bridge::start. Bridge::call (bridge.rs) checks only that the name is in self.tools, and serve_conn's `call` op accepts any such name. The allowlist exists only in run_client (bridge.rs:557 and keep_only), which is a process Pi itself spawns from a config file Pi can edit. The socket path is exported as THINKTIN_VAULT_SOCKET, the tool names sit in .thinktin/platform-tools.json, and the thinktin-vault helper shows the line protocol. Pi's bash runs without approval, so injected instructions can bypass the filter with a socket one-liner, or by editing ~/.pi/agent/mcp.json to drop `--only` and running /reload. The socket predates this change, and platform-side guards limit the damage. But the change's claim that 'Pi only gets web_search' rests on a filter the agent controls, so it is defense in depth only. Rated low.

修法：Enforce the allowlist in the shim process. In serve(), when `cfg.manifest.llm.config == ConfigGenerator::Pi`, retain only PI_PLATFORM_TOOLS in the tools passed to Bridge::start and in later set_platform_tools updates. Simplest is a `only: Option<Vec<String>>` field on Bridge that set_tools and call() check. Keep `--only` in mcp.json as a UX filter.

### [成立] [low] Stale ~/.pi/agent/mcp.json is left in place when a run starts without platform tools

Confirmed. exec.rs:170-184/135-141 passes `--platform-tools` only when launch.platform_tools is non-empty. That is possible when a grant's scope.platform_tools is empty: migration 0036 skips empty lists, and a user or plan grant can have none. Without the flag no Bridge starts and cfg.mcp_servers is empty. inject_mcp then returns at its first line, write_files never deletes anything, and .pi lives under the persisted home and state_dirs. The previous run's Bridge was dropped, and Drop unlinks the socket. So the old mcp.json still tells Pi to spawn `agent-shim mcp-bridge --socket <gone> ... --only web_search`. run_client fails at UnixStream::connect (ENOENT) and exits. Pi then reports a failed MCP server once after startup (docs/mcp.md 'Diagnose connection problems') for a server the run was never meant to have. The impact is cosmetic or noisy: no tools leak and the run continues. OpenClaw is unaffected because openclaw.json is fully re-rendered each start.

修法：In inject_mcp, handle the empty case per agent. For ConfigGenerator::Pi, always push `.pi/agent/mcp.json`, writing `{"mcpServers": {}}` when `servers` is empty, so the stale entry is overwritten. Keep the early return only for the OpenClaw branch (or drop it, since there it is a no-op anyway). Add a test that renders Pi with `servers = []` and asserts an empty mcpServers map.

### [成立] [low] Vendor searches are recorded as 0 when a stream is interrupted before the final usage or completed event

Confirmed by experiment. I extended the fake `/slow` upstream to send message_start, then a `content_block_start` with `server_tool_use` name `web_search`, then a `web_search_tool_result` block, then hang. The client dropped the response after receiving the search result, and the gateway recorded `outcome=ClientClosed web_searches=0`. `UsageMeter::on_event` only reads `usage.server_tool_use.web_search_requests` (Anthropic message_start/message_delta) and `response.output` in completed/incomplete/failed (Responses). It ignores content_block_start and response.output_item.done. Esc during Claude Code's multi-second WebSearch sub-call, or a Codex interrupt after web_search_call items, are ordinary user actions, and the vendor bills searches it has already run. The same zero shows up on an upstream stream error. Token accounting is deliberately conservative on these paths, but search counting is not. Impact is limited to under-reporting in usage records and the dashboard: vendor searches are not capped by our limits, so no limit is bypassed. Hence low.

修法：Keep a running lower bound in UsageMeter. For Anthropic, count `content_block_start` events whose content_block.type is `server_tool_use` and name is `web_search`. For Responses, count `response.output_item.done` (or added) events whose item.type is `web_search_call`. When the authoritative number arrives (message_delta/completed), set web_searches = max(running, final).

## product

### [成立] [low] Calls the vendor billed but our parser rejected are refunded, so the ¥100/month and 50/day caps do not limit them

The code path is real. post_json/IqsSearch return Err for a 2xx with no `pageItems`, for a reqwest timeout (the 15s whole-request timeout from [search].timeout_secs), and for a 3xx (redirects are off). search.rs:185-188 then settles with counted=false and actual=0, which refunds both the daily call and the money. IQS bills every request under 400, so those calls really are charged. The scenario is much less likely than the finding suggests, though. The IQS UnifiedSearch doc (help.aliyun.com/zh/document_detail/3062218.html) puts the server-side timeout at 5s, against our 15s client timeout, so a timeout after IQS has already answered needs about 10s of network stall. The doc also lists `pageItems[]` as part of every response and returns errors as 4xx (403 Arrears/NotActivate, 429 throttling), and none of those are billed. IQS is only the fallback after DeepSeek fails. Each mis-recorded call costs ¥0.008, so passing ¥100 would take about 12,500 uncounted calls. The DeepSeek case (a 200 with results whose body read then times out) is rarer still. So the accounting gap is real, but only an unusual vendor event triggers it and the money involved is small.

修法：Have SearchBackend::search report on failure whether the attempt was billable: for IQS, any HTTP status below 400 (also a parse failure after a 2xx); for DeepSeek, a 200 whose results were non-empty. Settle with the sum over all billable attempts, and keep the call counted whenever any attempt was billable.

### [成立] [low] Pi's 'only web_search' limit lives only in the MCP client; Pi can still call every granted platform tool through the shim socket

Confirmed, but this change did not introduce the exposure. executor.rs:837-844 sends every granted tool (delegate, schedule_*, board_*, artifact_*, computer_* when a computer is connected) to every harness, including Pi. The finding overstates one part: high-risk computer_* actions still need the user's signed approval on the phone (computer.rs:10-11).
