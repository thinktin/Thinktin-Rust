# 常驻可靠性演练（WBS 7.15）

目标：计划运行跑到一半时出事，不用人管，平台自己把它跑完，结果照常进收件箱。自动演练在 `crates/e2e/tests/reliability.rs`，每次推送 CI 都跑。

## 怎么演练

每个副本是一个完整的 `thinktin-server`（调度、执行、投递、巡检），在单独的线程和 tokio 运行时里，用自己的连接池和节点名。“杀副本”是直接丢掉整个运行时，不走优雅停机，效果和 `kill -9` 一样：租约不交回、连接直接断、沙箱进程没人收拾。agent 是真实的 agent-shim 加假 agent，任务要跑 10 秒左右，跑到一半时出事。

每个场景都核对：运行最后成功；是第 2 次尝试（同一个运行，不会多出一个）；第 2 次的任务前面有续跑说明（“这是第 2 次尝试，上一次执行中途中断了……”，7.12）；恢复用了多久。

## 场景和结果

| 场景 | 怎么模拟 | 平台怎么恢复 | 核对 |
|---|---|---|---|
| 杀 agent 进程 | 杀掉沙箱里的 agent-shim 和 agent（`kill -9`） | 执行器看到进程退出，按崩溃重试：等第一次退避（`retry_backoff_secs`）后同一个副本重新领取，唤醒时沙箱还在，在原来的沙箱里起新的 shim，会话能接回就接回 | 成功、第 2 次、续跑说明、沙箱 id 不变 |
| 杀副本（宿主机宕机） | 丢掉副本的整个运行时，本地沙箱随之消失 | 租约不再续，过期后另一个副本的接管扫描（`takeover_every_secs`）把运行转入退避，退避后领取；唤醒时发现沙箱没了，按模板重建、挂回工作区卷 | 成功、第 2 次、续跑说明、沙箱是新建的、恢复时间不短于租约剩余时间 |
| 发版重启（滚动） | 新副本先起来，再让老副本优雅停机 | 老副本停机时停下 agent、交回运行（立即可领，不等租约），新副本马上领走 | 成功、第 2 次、续跑说明；租约设成 120 秒，恢复远快于它 |
| 退出登录、关 App | 用户退出登录后计划到点 | 计划用自己的运行授权跑，和设备会话无关；再登录时收件箱有结果、事件按序号补回 | 见 `main_chain.rs` 的常驻场景（17.3） |

## 恢复要多久

- 杀 agent 进程：约等于 `retry_backoff_secs`（默认 30 秒，之后每次翻倍，最多 30 分钟）加重新起 agent 的时间。
- 杀副本、宿主机宕机：最坏约 `lease_secs + takeover_every_secs + retry_backoff_secs`，默认 60 + 15 + 30 ≈ 105 秒，再加重建沙箱的时间。要更快就调小 `[worker]` 里这三个数；租约不能小于 4 秒（每四分之一个租约续一次），调小了会增加数据库写入，也更容易把一次长时间的 GC 或网络抖动当成宕机（副本自己续不上租约时会主动停下这一轮，不会两个副本同时跑）。
- 发版重启：老副本停机的时间（`[shutdown] grace_secs` 之内）加新副本的领取间隔（1 秒）。

运行默认最多尝试 3 次（计划运行），中断都算一次尝试；超过就判失败并通知用户。等审批、等 key、等子任务的时候不占执行名额，从这些等待里接着跑也不占重试次数（见 7.10、7.11、8.7）。

## 预发环境上再做一遍

自动演练用的是本地沙箱后端：副本被杀时沙箱跟着没了。真实部署里沙箱在 Cube 上，控制面副本被杀时沙箱还在，接手的副本唤醒时会直接恢复原来的沙箱，比演练里的重建更快。等 2.3 部署后在预发环境手动做一遍，记录恢复时间：

1. 建一个要跑几分钟的计划（比如让 agent 分步写一份长报告），等它开始跑。
2. `kill -9` 正在执行它的那个 `thinktin-server` 进程（看运行的 `lease_owner`），记下时间，看另一个副本什么时候接手、运行在不在原来的沙箱里接着跑。
3. 关掉沙箱所在的 Cube 节点，看沙箱丢失后能不能从模板加工作区卷重建（整机快照恢复等 Cube 联调，见 6.6、7.12）。
4. 按发布流程滚动发版一次，确认运行马上交回、没有等租约。
5. 退出 App 登录、手机关机一晚，第二天看计划有没有按时跑完、收件箱和推送对不对。
